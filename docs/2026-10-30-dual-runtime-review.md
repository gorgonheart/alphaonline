# 双运行方案审查与开发计划

日期：2026-10-30。审查对象：`2026-10-30-dual-runtime-plan.md` v2、其引用的预热解耦计划，以及当前两端工作区代码和未提交修改。

状态：**审查完成，待人工确认开发范围；未实现本计划，未部署、重启或下单。** 此前“人工审核确认”覆盖上一轮预热接入与 select_coin 的 14 行修改，不自动涵盖本轮新增方案。

## 1. 结论与建议

“本地用完整历史生成状态，服务器只读取最近 4050 根 Arrow 并续算”方向可行，但原 v2 不能直接实施。应先证明完整状态可恢复、因子输入等价、后续新小时结果一致，再讨论性能。**不采用 P 批先上线的容差放宽方案。** 保留当前严格校验，允许增加定位差异的诊断信息。

本方案的三个历史长度必须区分：

1. **因子计算输入历史**：生产者仍需完整历史；4050 是交易消费者的读取窗口，不能把服务器生产者也缩成 4050。ILLQ 长窗口、CciV3 和有状态动量不是在尾窗重算。
2. **消费者行情窗口**：最近 4050 根已闭合、同一 offset 的小时 K 线，附带完整历史预计算得到的因子列。
3. **策略及模型状态历史**：保留本地初始化以来的子策略净值、再择时、组合/虚拟账户、训练样本等；不能随行情一起裁到 4050。当前实现会继续增长。

“无需重新初始化”应定义为：服务器恢复同一截止时刻的完整计算状态，只推进 T 之后的缺失小时，首次在正常 offset 时刻按实时资产生成目标。它不代表不用补算、不用在 Linux 编译扩展、不用检查新行情，也不代表补发历史订单。

## 2. 已确认的阻断问题

### A. 账户运行配置改变会被预热包拒绝

`tools/robust40/warmup.py::settings/prepare_startup` 将 `get_kline_num`、`get_kline_num_spot`、`required_history_start` 放在包的配置一致性比较中。原计划把 14050/固定起点改成 4050/None，启动必然报配置变化。

不能直接删除这些比较：部分字段目前确实影响因子初始化和策略语义。应拆成“必须相同的策略计算定义”和“经本方案验证允许不同的部署配置”，只允许明确的 full-bootstrap → arrow-resume 转换；保留最小上市时间、S3 起点、因子参数、币池过滤、模拟器、调仓和分钟的严格比较。

本次只读检查还发现：**20/40/55m 当前配置均已与其活动预热包的 strategy_pool、precompute_factor_configs 不同**，更新后的 ILLQ 参数尚未进入旧包。另一个 `40m_run1` 包也存在这些差异。上轮“包与配置相同”的结论仅对应当时版本。本轮必须由当前冻结配置重建，不能编辑包内字段冒充兼容。

### B. S3 持仓状态没有真正接入框架增量链路

`sections/VolumeMaxBias_进出场阈值分离官方.py::signal` 支持 `df_prev`，但 `core/select_coin.py` 的 Pandas 调用只传三个参数；Polars 适配器也调用三个参数版本。当前两条路径都重新从固定日期初始化该截面因子。

S3 需要起点前 720h 数据。现在起点为 2026-08-01，要求最早覆盖 2026-07-02。随着 4050 根窗口右移，约 2026-12-17 前后便无法满足；不同分钟和上市过滤可能更早触发。已用 2027-01-01 00:20 结束的 4050 根时间轴复现其初始化报错。

现有预热包包含选币、ratio、模拟器等 snapshot，**没有框架持久化的 S3 截面状态**。`选币结果.pkl` 是经过后续过滤的结果，不能直接当作完整的截面持仓标记。

应在共享截面框架增加显式启用的状态传递接口，并由原 VolumeMaxBias 模块提供状态内容与恢复规则：保留最后有效截面的完整成员、因子值，以及重建延迟排名所需的历史。状态按账户、offset、因子及参数隔离，与子策略 snapshot 同截止、一起导出恢复。不得创建 Robust40 专用因子副本或在 core 写死 S3 名字。旧策略未启用时保持原调用方式。

### C. 12 列预计算不足以覆盖全部长依赖

现配置 12 个唯一列来自四个动量、五个 ILLQ、三个 CciV3 参数。还必须展开 section 的 `get_factor_list` 依赖，不能只检查账户显式长窗口。

已确认 `TopKTo2K(168, Cci过滤无现货删数据, 2600)`：基础 CCI 先 rolling(2600) 计算均值，再对偏离值 rolling(2600)，完整支持需要 **5199 根**；叠加 TopK 的 168 根历史排名，影响范围可达 **5366 根**。它不在当前 12 列中，生产者目前也没有该同名因子文件。

独立构造同一条 14050 根行情，直接调用当前基础因子：全历史末值 94.90455908028679，4050 尾窗末值 97.4235354524378，差 2.518976372151016。这证明存在数学差异，不等于声称所有真实时点都会翻转选币。

优先将必要的长依赖加入生产者预计算，并复用相同因子公式；前提是其现货/合约映射等输入已与消费端对齐。若输入顺序或映射处理不同，必须先解决，不能只复制文件、增加列名。对其他因子完整展开串联 rolling、异常重置和 EWM 依赖，得到实际必需列；短窗因子仍可在 4050 内计算。

保留因子独立 oracle 的先失败后修复流程。任何共享公式变动都属于单独人工审核项，本计划不为追求一致性修改公式。

### D. “14050 根就能跑满模型”的验收不成立

14050 个连续小时观测跨度为 14049h，即约 585.375 天；这不等于 585 天有效策略净值。

当前 `process_equities/read_children` 取各子策略最晚开始时间作为共同起点；S3 的 2026-08-01 起点把模型可用区间限制在近期。实读 `40m_run1` 包：共同区间 2026-08-10 00:40 至 2026-10-29 23:40，1944 根；prediction 仅 81 个观测日，季度模型数 0，weekly_mix 非基础行数 0。

`robust_weekly_mix` 是最近最多 365 日、至少 180 个有效日、周一更新；季度模型是最多 365 日训练窗、48h 隔离、至少 180 个采样日，并要求两类标签。**没有“365+180 必须相加”的代码条件。** `virtual_accounts[0].index` 是小时轴，长度 ≥365 不是 365 天。weekly_mix 选择纯基础组合可以是正确结果；不能强制它必须选专家。S5 在某个时刻 delta 为零也可以合法。

需人工确认的策略选择：若本次目标包含上线即具有成熟的周混合/季度模型，必须重新评估 S3 固定起点及有效样本区间，再独立重建各 offset 基准；这会改变历史策略行为，不能夹在“切换数据源”里实施。若保持 S3 日期，则可以接续当前策略，但不能宣称已激活完整模型。原解耦文档“不改 S3 日期”的要求与“上线前成熟模型”的目标存在此冲突。

`required_history_start='2025-10-28'` 仅校验覆盖这个日期，至 2026-10-30 约 367 天，不保证 14050 根。当前固定历史分支还会保留全部 PKL，设置 get_kline_num=14050 并不会自动精确裁到 14050。

### E. 不能通过容差放宽保证衔接

原计划 §1.3、§3.0 的推论有误：虽然旧重叠行多数保留，`merge_context` 用重叠末点估算 scale，随后追加的是 **new 的新增净值 × scale**；新持仓、再择时及市场输入也进入新增状态。相同的错误来源可持续影响新增小时。S3 又是持仓递推，positions 也并非一概“非递推”。

正确迁移应恢复同一模拟器的 equity、lots、target_lots、last_prices、lot_sizes、再择时等状态，而不是在服务器用短窗重新开一条净值再缩放。恢复同一状态后，不应先假设必然存在千分之一量子化偏差。

文中 `0.5 × sqrt(504)` 是假设计算，不是可核验实测：0.5 手还要乘币数单位和价格才是 USDT，误差也未证明独立。不能据此把净值阈值直接放到 1%。阈值表还存在 warn=fail 的空区间、positions 在 warn 模式实际允许到 1e-2 却宣称 1e-4 严格等矛盾。

保留严格拒绝历史修订；增加差异位置、最大绝对差、零/非零持仓集合和数量等诊断即可。若实际 Linux 对拍发现浮点小差异，再用真实证据确定容差；离散选币和目标手数仍需一致。`transform_targets` 是框架与同一运行模型的内部一致性检查，不能替代跨运行环境的独立对拍。

### F. 子策略长历史与短行情还需适配

恢复后 `account_state0/1`、ratio 和处理后的 equity 可能保留全部本地历史；`live.build_context` 却要求这些 index 全部出现在本轮 pivot。只改 raw 的 PKL 读取不能解决此要求，历史继续增长后也会超过生产者滚动 pivot 的长度。

建议在 `tools/robust40/live.py` 中，以本轮实际可用行情构造一个**共同尾部 incoming context**，同时裁 equity/ratio/leverage/pivot 的视图；旧 MODEL context 保留完整历史并追加新增行。此调整不做 Tail-Only、不把旧状态裁短、不改变 core 仓位聚合。

raw 特征行情保留未过滤的同批次 swap 数据、真实 first_candle_time、成交量/主动成交量/费率/avg_price_1m 等字段；不能直接复用已经过黑名单或可交易过滤的选币 dict，BTC 参考行情仍需保留。选币和 raw 可以复用既有 Arrow reader，没必要为 MODEL 在 core 新增专用 load_raw_swap。

已有 child 模拟仍依赖 pivot PKL、exginfo；“交易端读 4050 Arrow”不等于可以只部署 Arrow、删除生产者 PKL/pivot。首版保留现有发布链路。raw、spot/swap Arrow、pivot 需同轮完整，避免读到新旧混合发布。

### G. 因子输入口径必须比“根数相同”更精确

alpha 当前 kline_count_1h 为 14060，重采样数量可能不同，Arrow publish_kline_num=5000；不是原计划假定的两个阶段都精确 14050/4050。CciV3 和有状态动量有初始化路径，不能把 14050 与 14064 的差异自动归为浮点误差。

实施前固定本地及服务器生产者的输入时段、初始化方式和闭合根处理；完整输入上先算因子，再裁出消费者所需行。有限窗口虽可在满足依赖后等价，不能将此结论推广到所有状态因子。

一次性全历史回放，与每天从不同起点重算长因子的滚动生产流程，历史因子值也可能不同。验收必须包括相同历史发布序列的逐小时重放；若要求与“一次性 14050 全量回测”全程相同，还要单独证明该生产序列口径相同。若不成立，需另审生产者状态续算/历史因子记录方案，不能放宽校验掩盖。

## 5. 建议的配置和衔接方式

共用一份策略定义，通过两个运行配置描述差异，不复制两套容易漂移的 strategy_pool：

| 项目 | 本地初始化/验收 | 服务器续算 |
|---|---|---|
| 策略、因子参数、S3起点、模拟/执行规则 | 同一经审核版本 | 相同 |
| 因子计算语义 | 冻结完整输入及算法 | 相同输入口径，在生产者完整计算后发布尾部 |
| 消费者模式 | full-bootstrap，目标14050闭合小时 | arrow-resume，4050闭合小时 |
| 起点要求 | 固定初始化起点及实际完整数据校验 | 包记录同一起点；读取窗口不强求覆盖它，状态必须已恢复 |
| 启动状态 | 显式新建隔离目录 | 必须有完整配对包或已推进的完整状态对 |
| 环境差异 | Windows路径、测试规则数据 | Linux路径、实时市场/账户接口 |
| 数值检查 | 严格 | 严格；不默认warn/off |

如果上传耗时导致落后多个小时，按顺序补算到 E，最终仅生成当前 E 对应的目标；不发旧时刻订单。若本轮输入不能覆盖最早缺失小时的依赖，在本地推进并导出新包。

## 8. 全5分钟offset的成本与运行约束

每个offset仍每小时运行一次；12套意味着每小时12次，生产者同样12次长历史预计算。当前 startup 串行运行匹配账户，存在23s休息和统计任务；不能只依据 advance<40s 判定能承受每5分钟频率。

先测生产发布延迟、完整账户轮次p95/p99、跨日/季度峰值、统计并发、状态序列化及内存，再验证每300s到下一offset前有余量。生产者新backfill只在未启用offset的空档运行；全部12个启用后没有这种空档，不能依赖它自动补全其他offset，应部署前分别预热。

不要直接并行启动12个交易进程：现框架共用 data/cache、data/runtime 并会清理它们。保持现有串行流程；若容量不够，独立工作目录/调度拆分应另案人工审核。

4050只减少行情输入，不减少当前MODEL全历史context、9个虚拟账户、价格矩阵和不断增长的训练历史。小包81天的耗时/121MB不能外推为成熟585天在8GB服务器可用。按实测包大小估算12份磁盘、导入暂存、上一完整状态对及峰值内存，留出生产者全历史/Arrow/pivot空间；本轮不做自动历史裁剪或毫秒级承诺。
