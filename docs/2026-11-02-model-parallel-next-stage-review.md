# MODEL 并发与下一阶段优化复查

## 结论与授权边界

**最新业务架构澄清优先于下文早期假设**：生产上游是alpha，alpha2目前是验证环境。两套独立alphatrade程序目录分别运行5/15/25/35/45/55m和10/20/30/40/50m；每套正常交易循环串行。当前目标是保证同一套内55m后台初始化与后续5m正常交易不互删，并利用错峰空闲CPU，不是实现同一程序目录多个正常交易账户的并发流水线。因此“为所有正常账户重构临时目录并改异步调度”不列入本轮开发。末节有本次路径审计及验证。

2026-11-02，用户已确认上一批三个 core 文件的修改。用户进一步明确：初始化与续算分别评估，争取在控制峰值内存的情况下使用3/4并发；S3中间切分方式可调整，但最终模型与策略结果必须一致。

本轮是代码审计、离线抽样和计划更新，不新增业务修改，不将现有 MODEL_JOB_NUM=1 直接改成4，不部署、重启或清理生产数据。上一批core确认不等于后续core修改的自动确认。

初步结论：值得继续做一批小范围优化，重点是释放无用大对象、消除嵌套并发、时序因子重复计算和输入副本。继续全面重写S3为C++、季度模型缓存或整仓迁移技术栈，目前投入收益不合适。3个worker是优先测试目标，4个是对照项，不是所有阶段必须同时达到的数量。

## 初始化、续算、回放必须分开

| 场景 | 实际工作 | 主要资源风险 | 衡量方式 |
|---|---|---|---|
| 首次/失效后完整初始化 | 140xx PKL完整因子、截面/子策略全历史模拟、MODEL历史及恢复点 | 全量原始列表、因子结果、S3/其他截面、各模拟进程重复Pivot | 从冻结到状态提交的完整时间、整棵进程树峰值、同机可用内存/换页 |
| 正常小时续算 | 4050 Arrow中的12个预计算列复用，其余时序因子仍计算4050输入；选币/子模拟追加；MODEL校验与状态追加 | 全市场4050因子结果、历史状态读取/合并；并不等于只算一根K线 | 热缓存新进程整轮P50/P95，分阶段时间与峰值 |
| 跨日/季度续算 | 正常续算加已有按需原始行情读取、特征/季度评分或训练 | 日界输入及历史特征，不应混入普通小时P95后隐去差异 | 单独统计跨日和季度事件 |
| 修订回放/停机追赶 | 共同恢复点、修订范围重算、S3和子模拟共同恢复 | 原状态与工作状态并存、复制/恢复、多小时计算 | changed_fields、回放小时数、copy/restore/compute耗时及峰值 |

`positions/ModelRobust40Strategy.py::merge_context`仍追加历史持仓矩阵、equities、simulation行情和close；`core/equity.py::create_ratio_snapshot`仍合并历史持仓。4050不是所有状态的统一上限，也不能用4050/14050推导全流程内存比例。不应为降内存随意裁掉季度/回放/模拟依赖的旧状态。

另一个重要区别：4050约束的是该轮Arrow K线输入，`read_bmac_market_pivot`仍直接读取上游相应目录的Pivot PKL，随后才在模拟中按时段/币种裁切。上游Pivot保存140xx时，正常续算也会先读入这些历史；get_kline_num=4050并不会自动限制Pivot反序列化的峰值。

## 当前并发的真实含义

- `MODEL_JOB_NUM`覆盖时序因子池、因子写盘线程，以及子策略选币/聚合/模拟三个池；这些阶段前后执行，不能把阶段峰值直接相加。
- 时序因子每个任务是一币种/市场的完整输入，不是把整市场复制到每个worker；但父进程一直保存全部原始列表和当前分片结果，worker/IPC另有副本。
- 有界提交上限为2×worker：3/4分别最多6/8个在途任务。这限制排队副本，不限制父进程的全输入/全片结果，不能把它当整机内存限额。
- 初始化选币因没有snapshot，内部串行；正常续算 `multi_process=True`，每个外层进程还有 `max(job_num//2,1)` 个线程。3对应最多3×1个选币任务，4对应最多4×2=8个任务，尚未计入Polars/BLAS内部线程。这是3到4可能突然抬高峰值的具体原因。
- 截面/S3没有随MODEL_JOB_NUM变成3/4个S3进程；截面分片1控制同时计算的参数组。Polars本身仍可能多线程。
- MODEL专家、季度评分及有状态模拟不是上述池中的独立无状态任务；修改MODEL_JOB_NUM不会自动并行这些数学模块。
- `Coordinator`只限制同一startup实例一个初始化任务，已ready账户仍可在前台运行；其他安装实例也不共用这个初始化槽位。单账户3worker不代表全机只有3worker，不能在8GB机器上同时启动3/4套完整MODEL初始化。

## 1/3/4 worker的离线对照

可复跑入口：`research/model_parallel_20261102.py`；有效结果 `research/model_parallel_20261102/controlled/result.json`。

真实55m BTC/ETH/BNB/SOL/XRP/DOGE/ADA/LTC现货与合约，共16帧；各重复4次成为64个独立任务以摊薄启动开销。初始化14050行、16列分片，共5个进程池；续算4050行、80列一片，已断言12个预计算列存在。调用当前真正的 `process_candle_df_return_polars` 和有界队列，保留返回顺序，逐表精确比较所有worker结果。

Windows alpha311，限制到4个逻辑CPU，各进程Polars/BLAS/OpenMP/Numba线程数为1。计时包括池启动、派发、因子计算、返回和拼接，不包括因子文件保存；每20ms采样进程树RSS，RSS求和可能重复统计共享页。16个源输入重复引用使父进程基数小于64个不同币，更远小于924币全市场。该基准用于比较并行开销，**不能外推为Ubuntu全流程4GB内存验收或P95**。

初轮对拍发现 `BacktestConfig.load_strategy_config` 的 `list(set(self.factor_col_name_list))` 让独立进程分片组成不同，导致按分片文件比较列名不一致；不能将这一失败当成因子数值不同。初轮性能数字不用于最终配对结论。实验修正为生成conf后仅在实验中排序因子列，保证所有并发方案同样的分片组成，再重跑六组。生产代码不改；稳定分片可以减少重启后资源表现波动，未来按因子族分片也须先统一这一规则。

控制相同分片组成后的实测如下；每个单元为“秒 / 进程树峰值MiB”：

| 时序因子抽样场景 | 1 worker | 3 worker | 4 worker |
|---|---:|---:|---:|
| 初始化：14050行、16列分片 | 63.78 / 754 | 44.61 / 1140 | 46.43 / 1319 |
| 续算：4050行、80列一片 | 19.55 / 466 | 11.62 / 739 | 11.58 / 876 |

六组输出按完整表逐值、列序及类型精确对拍通过。3相比1，初始化样本耗时少约30%，续算少约41%；4对3未表现出明确速度收益，峰值RSS更高。每组一次受控运行，不能以4%的差异认定3在任何负载都更快，也不能把新进程/样本差异当统计置信结论。结论仅支持优先把3作为下一步全市场验收候选，4作为对照。

本次只是时序因子调度测试，未执行交易、完整子策略选币/模拟和MODEL回放；上一轮S3完整输出/状态/25点等价性证据仍有效，但不能说这六组新基准已经重新验证全部模型输出。

## 优先测试的分阶段配置（建议，尚未实施）

保持一个MODEL并发上限和一个功能资源入口；在tools中由初始化/续算模式派生阶段上限，不把资源设置放accounts，也不重新增加数个互不关联job_num。下面的1/2/3是待验收资源策略，并非当前代码已具备该分阶段调度。

| 阶段 | 初始化首选候选 | 正常续算首选候选 | 提升到4的条件 |
|---|---|---|---|
| 时序因子 | 3 worker，16列分片 | 3 worker，先保留80列一片 | 真实全市场较3明显更快，整机峰值/换页可接受；不能只测单币 |
| 截面/S3 | 同时1组；S3时间块顺序执行 | 保持状态续算，避免并发全历史截面 | 不以开4个S3进程为目标；评估Polars线程而不是复制4份输入 |
| 子策略选币 | 先1，测量后2 | 外层最多3，内层固定1 | 先去掉4×2放大，再测3/4；完整初始化不能照搬续算结果 |
| 权重聚合 | 先1，测量后2 | 取消无用矩阵回传后测试2/3 | 大矩阵回传/保留问题先修；进程数不能解决该问题 |
| 子策略模拟 | 先1，测量后2 | 先1/2，按Pivot峰值决定是否3 | 当前每个任务都读取Pivot，内存与IO没有共享；不能默认4安全 |
| MODEL状态/专家组合 | 保持现有单流程 | 保持现有单流程 | 有状态时间递推不直接并行；仅对证据明确的独立计算单独立项 |

本机抽样的线程限制只用于实验。若正式实施，应该在相应子进程导入数值库前设置，并验证实际线程数；不要给整台服务器/所有传统账户全局写死POLARS_MAX_THREADS=1，否则可能使单进程截面变慢。Polars官方要求线程池初始化前配置，且推荐多进程使用spawn：[线程池文档](https://docs.pola.rs/api/python/stable/reference/api/polars.thread_pool_size.html)、[多进程文档](https://docs.pola.rs/user-guide/misc/multiprocessing/)。

只在阶段入口选择预先测试的固定配置，避免逐币读/proc、反复扫描行情或构建新的校验注册表。整机验收用系统/进程树采样，Linux优先看服务进程组或PSS/cgroup，并同时看MemAvailable、持续换页与其他实例。3worker为其他任务留出的是调度余量，不是CPU/内存的硬隔离保证。

对于时序阶段，可以按“父进程基础+全输入+当前结果片+N个worker工作集+在途传输+同机其他任务”核算峰值；不是简单把完整父输入乘N，也不是只算N个子进程。完整初始化约1141万行，仅16列float64的数值缓冲就约1.36GiB，尚不含行情/对象列/有效性位图/计算临时数组；因此分片后的实测仍是必要条件。预算应按同时存在的对象与进程叠加，前后不重叠阶段取最大值。

## 本轮审计新发现：高收益、小范围候选

### A. 权重聚合返回值无消费者，但大矩阵仍被传回并保留

`core/backtest.py::_step5_worker`返回 `step5_aggregate_select_results` 的两个持仓DataFrame；后者已经写到每个子策略目录，下一步模拟再从文件读取。父进程仅调用 `f.result()` 检查异常，不使用这些矩阵。`futures`字典在循环结束前一直引用已完成Future；完成/调用result并不清除Future内部结果。

因此产生无用的大矩阵序列化、传输、反序列化和父进程累计持有；**改1worker也不能根治累计保留**。初始化结果长，收益预期更高；续算也存在但须按实际矩阵大小测量。

最小候选：仅让私有 `_step5_worker` 调用原函数后返回None，保留公开step5函数返回接口、全部落盘和异常传播。不改模拟读取来源，不引入新文件。前后按全部持仓矩阵、模拟曲线及模型最终输出对拍，测试异常仍由父进程收到。这属于去除私有调度的无用数据回传，不取消用户功能，无需回退整段core。

### B. 嵌套并发应先有确定上限

选币外层池和内部线程都从同一个job_num放大。在MODEL入口为外层并行选择串行内层，或引入默认保持原行为的内部上限；只影响MODEL。传统策略默认不变。时序池底层线程在启动前限制；不能在已初始化Polars池中改环境变量后声称生效。

最小候选范围是tools资源profile、core/backtest.py与core/select_coin.py；不需要startup改动。这是调度约束，非功能取消。任何新增差异均需列出单独人工复核，不并入已确认的旧补丁冒充确认。

### C. 剩余内存成本不能靠S3优化消除

`calc_factors`仍一次read_pickle全量原始列表并保留整个因子分片的结果；分片16只缩小结果列宽。其写盘任务已显式del，不应再次把“整个上一片write_tasks没释放”当成新问题。首片kline投影视图及局部末帧仍可审查提前释放，但收益需测，不与全量列表问题混淆。

`calc_equity`每个任务读现货/合约Pivot，之后才按币种及模拟时段裁切；多个模拟进程同时解包同样的大输入。优先降低重复读取/限制该阶段并发，后续才考虑共享Arrow/mmap。给每个worker添加长期Pivot缓存可能扩大峰值且有币种裁剪/修改污染风险，不先这么做。

## S3允许改中间布局，但必须保留的验收边界

用户不要求固定168小时块、相同临时DataFrame或内存对象布局；可以继续调整。S3有历史持仓和排名延迟队列，**相邻时间块有递推依赖**，不能独立初始化4块后直接拼接。每个时刻必须保留完整有效币池，排名/并列顺序/空截面/进出场规则不变，跨块传递真实held和队列。

除了最终一次模型权重，还必须核对每小时S3选择结果、子策略持仓/收益/再择时、模型权重/目标仓位及恢复后结果；否则仅“最后一次相同”会漏掉中途交易差异。测试包括分块边界、空截面、并列排名、跨日/季度、停机追赶、修订回放和失败恢复。内部状态格式若改变，可按已获用户原则全量重算，不为兼容制造多套状态；不过当前优化无需改状态格式或清空已有数据。

## 下一阶段开发与验收顺序

1. 先实现A，测试不用pickle大返回值但落盘完全一致，异常仍传播；最小core差异单独提交人工复核。
2. 实现B及统一功能入口派生阶段上限，分别验证初始化、正常续算、修订回放；覆盖传统5/15/20/25/45策略默认路径，未提供真实账户时明确fixture边界。
3. 在Ubuntu隔离完整计算输入中比较3/4，初始化与4050分开测；包含父进程、计算子进程和后台初始化/已ready账户共存，不用本地16帧样本替代。
4. 通过后先做只改factors的多参数热点；逐项独立oracle和同输入性能对照，不一次改几十个因子。coin-cap作为独立core复核项。
5. 如果完整输入驻留仍超预算，再做按币种分批落盘；此时是内存必需项而非为了技术栈升级。无需为前四步引入持续内存扫描、新hash/manifest、账户参数或alpha修改。

整机预算以实际可用物理内存减生产者/其他账户峰值及系统余量计算，不把swap当安全内存额度，不仅看单个worker RSS。验收前不给出“3或4肯定安全”的结论；验收结果应能明确指出初始化与续算各采用多少并发、在哪个阶段限制、限制的实测依据。

## 补充：实盘旧版仓管到下单阶段资源低（用户现场观察）

用户提供2026-11-02轮次：子策略模拟28.994秒，累计161.713秒，资金曲线截止04:55 UTC；随后出现“MODEL仓管：开始准备输入及续算状态”。用户观察此后含下单约10～20秒，CPU/内存利用率低。本轮未重新连接服务器采样该段，不能据此声称已定位到IO等待、单线程或锁等待中的某一种原因。4核平均CPU较低也可能是一核忙，需区分进程CPU时间和墙钟时间。

这一信息降低了继续重写正常小时MODEL数学内核的优先级，支持优先优化前面的时序/选币/模拟，以及评估后半程和其他独立任务的重叠。按该样本粗算，后半程减半仅节省单账户整轮约3%～6%；跨账户流水线是吞吐优化，不能和单账户延迟优化混为一谈。该观察不覆盖首次初始化、季度冷编译或修订回放的资源峰值。

当前实际依赖为：子策略模拟→process_equities→prepare_live（读状态、行情、整理输入、续算并保存）→calc_ratios/agg_pos_ratio/仓位限制→transform_targets与计算提交→保存目标→calc_target_position（更新账户余额/持仓及最新价格）→下单→资金归集/记录。仓管状态推进、目标校验与同账户交易不能直接并行；现货卖出、合约操作、现货买入也不能因CPU空闲就取消当前资金与执行顺序。

可评估三种不同的并行，按成本排序：

1. **单账户只读准备**：状态与必要行情等独立读取，最多2线程作对照，复用已有输入优先；减少等待，不创建3/4份大状态进程副本。读取仍需同轮截止时间、账户锁和修订一致性。spot/swap报价请求可另行测量，但要检查共享客户端/限流及新鲜度，不在耗时仓管开始前提前固定余额/持仓供稍后下单。
2. **不同账户阶段重叠**：A账户仓管/网络阶段与B账户时序计算重叠，理论上比给10秒尾部增加4个进程更有吞吐价值。但当前不能直接将startup的subprocess.run改Popen：普通trade仍使用安装目录下共享data/cache和data/runtime；run_by_account启动会删除这两个目录，calc_target_position又从共享runtime读目标，交易末尾仍读取选币cache。账户snapshot锁不能保护这些跨账户共享目录。必须先按账户/轮次隔离所有临时产物及外部信息缓存，并保持同一交易账户串行执行；隔离后再测叠加峰值。独立配置文件名不自动意味着独立交易所资金账户。该项涉及startup/目录协议，超出当前两文件最小优化批次，列为后续条件项目，不直接实施。
3. **相邻5分钟offset重叠**：需要下一轮数据ready才有可执行工作；当前样本约172～182秒，小于300秒，单个每5分钟任务未必会与下轮发生重叠。同offset多账户或异常长轮次时流水线才更有价值。不能为填满CPU提前使用未完成K线，也不能推断11个offset在所有负载下必然来得及。

因此下一阶段仍先实施无用聚合回传/嵌套并发治理及3worker时序验收；仓管后的只读等待有证据再小改，多账户流水线先证明临时目录隔离和需求收益。当前不新增core/startup/策略业务修改，不改下单先后顺序或预取账户资产。

## 补充输入2～4：错峰窗口、提前准备与资源优先级

用户说明策略错峰运行，通常存在约200～250秒可供初始化使用四核的窗口。该时间是用户运行设计输入，本轮未独立测量所有实例。据此修正之前“优先3worker”的理由：不固定为其他程序空留一核；初始化CPU并发上限可以以4为候选，实际3/4仍以Ubuntu同数据吞吐和内存为准。本地样本4没有明显收益，不代表服务器四核不能用满。保持一个完整初始化作业，在其中并行币种/独立任务；不同时开启4个offset的完整初始化。

200～250秒不是新的初始化截止时间。超出窗口后让上游/实盘优先，初始化继续低优先级计算，不在第4分钟报错、抛弃已算状态或重新起算。CPU空闲不等于其他进程释放了常驻内存；8GB内存约束仍需分片与阶段并发控制。持续初始化若跨过下轮上游更新，则既有同轮冻结保证它继续使用已绑定的输入。

### 当前ready顺序与可前移范围

当前 `startup.run_loop` 在 `sleep_until_run_time` 返回后，先调用 `check_bmac_update_flag` 等spot/swap ready，之后才按账户offset调用 `Coordinator.command`；后者再等spot/swap/Pivot四个同轮ready，随后recover_interrupted/inspect、Arrow列检查，最后Popen初始化。故目前确实在ready之后才进行初始化判定和启动准备。

启动器本来就提前随机60～120秒唤醒。建议在等待上游之前加一个轻量MODEL preflight，并保留ready后的最终判定：

| 时点 | 可以做 | 不能提前当作有效输入的内容 |
|---|---|---|
| 提前唤醒/进入目标offset | 识别账户/offset，检查已有job与锁，读取warmup小元数据和固定文件stat，核对配置/S3日期；确定本地缺状态等初始化原因 | 当轮ready尚未存在不能因此判为Arrow损坏或强制重建 |
| 已确定需要初始化、等待ready | 单个低优先级隔离准备进程导入模块/解析配置/展开依赖，复用已有Numba磁盘缓存；仅在有收益证据时准备必要代码缓存 | 不读取并冻结上一轮行情充当本轮，不提前重训，不批量启动4个空闲重worker占内存 |
| 同轮四ready齐全 | 快速复核账户配置/状态及publication，冻结行情/外部数据/自动bStocks规则，沿用同一准备进程进入读取计算 | Arrow缺列、当轮历史覆盖与修订仍需此时实际输入才能判定 |

`inspect`现有设计只读小元数据及固定文件stat，不反序列化大model/ratio，适合前移复用；不新增全盘扫描或hash。若旧worker仍持锁/初始化未完，预检返回忙，不把进行中的incomplete误判为应另起初始化。ready前本地“可续算”只是初判，ready后仍可能发现Arrow缺列或不可恢复修订而转初始化。

准备结果应由同一worker继续使用，不能先导入一遍退出、ready后再起新解释器。当前调度将正式work目录存在解释为本轮已尝试，而initialize又用exist_ok=False创建目录；因此提前准备不能抢先创建该正式目录。保留原工作目录创建在ready后，准备阶段仅用调度内存状态/独立进程；异常或配置变化时废弃准备，不修改生产snapshot完成标记。公共市场网络刷新若将来前移，必须单独验证发布时间/新鲜度，本阶段不为省时间冻结旧规则。

### Linux优先级：可行，但要控制整棵任务树

只读核实当前服务器：内核6.8.0-90，systemd255，cgroup v2具有cpu/io/memory控制器；alpha2、alphatrade及所观察PM2相关进程目前nice=0，并同属 `user.slice/user-1000.slice/session-23.scope`。这是当前未区分资源级别的状态，不是已配置三层优先级。

建议两层实施方式，按改动规模选择：

1. **最小代码方式**：上游alpha2保持原nice=0；只对alphatrade子任务在创建数值线程/子进程前设置主交易worker nice=+3、初始化worker nice=+10（候选值，待实测）。更大的nice值优先级更低；继承到后来创建的计算子进程。优先让整个初始化任务树低优先级，不逐个Python Future或线程调权。无需改alpha代码，也不必为上游设置需要额外权限的负nice。不要在PM2总父进程上统一降优先级，更不能在初始化工作结束后依赖无权限的反向renice来变成交易进程；初始化与交易本来是两个入口。
2. **资源隔离方式**：上游、实盘、初始化分别放入共同父级下的三个cgroup/systemd scope，按高/中/低CPUWeight分配竞争时的份额。权重是相对份额，不是固定核数/CPU配额；其他组不忙时，低权重初始化仍能使用所有空闲核。当前都在一个PM2 scope中，仅改该scope权重无法区分三个任务，须先有独立组与相应管理权限。这属于部署资源配置，不能仅添加一个Python线程参数就声称实现。

优先级降低不限制常驻内存，也不保证磁盘IO让行。若进入cgroup方案，再按整机实测预算设置初始化MemoryHigh及最后防线MemoryMax，必要时测IO控制器/设备调度是否有效。MemoryHigh会触发回收/节流，MemoryMax超限可能OOM终止初始化；二者都不能替代降低算法峰值，更不能把被终止初始化视为成功。未测总预算前不写死4GB/6GB限额。CPU权重是公平调度而非严格实时优先级，不采用SCHED_FIFO/RR，也不使用SIGSTOP暂停来假装释放内存。

官方依据：[Linux nice及继承](https://man7.org/linux/man-pages/man2/setpriority.2.html)、[cgroup权重分配](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)、[systemd资源控制与内存限制](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html)。在线文档为最新版本；服务器已核实255，具体部署选项/委派权限还须在落地时核对，不认为控制器存在就已授权或启用。

## 最新架构下：55m初始化与5m实盘隔离结论

以其中一套独立程序根目录R为例（另一套有自己的R，不共享可写cache/runtime）：

| 产物 | 55m后台初始化 | 5m正常实盘 |
|---|---|---|
| 计算根目录 | W=R/data/server_initialization/55m账户/stamp | R |
| 临时因子cache | W/data/cache | R/data/cache |
| runtime | W/data/runtime | R/data/runtime |
| 子策略与仓管计算结果 | W/data/子策略回测结果等 | R/data/子策略回测结果等，含账户前缀 |
| 计算中的snapshot/S3/MODEL状态 | W/data/snapshot/55m账户_策略名 | R/data/snapshot/5m账户_策略名 |
| 初始化成功安装 | 仅切换R/data/snapshot/55m账户_策略名及其.previous | 5m账户目录不在该目标下 |
| 初始化成功清理 | 仅精确匹配W的目录 | 不删除R/data/cache、runtime或5m状态 |

依据：initialize把workspace写入ROBUST40_SERVER_WORKER.root，compute及spawn子进程在import config/core前由configure_worker设置path_kit.PROJECT_ROOT。普通实盘虽然清理R/data/cache/runtime，但初始化使用W下的同名目录；S3状态通过conf.get_snapshot_folder，MODEL通过独立state_path。初始化计算不调用run_by_account交易入口。install限定单账户直接子目录，cleanup_initialization只接受由root、账户名、stamp确定的精确路径。

故按当前代码和上述目录架构，55m初始化超过10分钟也不应被5m正常交易的清cache/runtime破坏；文件隔离不依赖初始化必须在10分钟内结束。正常交易仍由subprocess.run串行，同一安装没有同时启动两个普通交易清理流程；10分钟更多是按时赶上下一个offset的预算。若重启、手工改目录/共享data链接或同时启动第二个同根startup，属于另一个运行条件，不包含在此结论中。

已用alpha311复跑5项针对性离线验证：初始化及实盘spawn配置路径传递2项、仅清自身workspace1项、安装失败回滚1项、上游替换/工作区清理后冻结输入仍有效1项，全部通过（28.57秒）。pytest缓存目录权限警告未影响测试。该批是路径/生命周期测试，不是服务器真实55m初始化与5m下单同时运行的全流程压力测试。

后续保持此结构：优先做ready前轻量预检/单worker准备、初始化低优先级、初始化阶段允许4核上限并按峰值约束；正常实盘与上游优先获得争用资源。上游alpha代码不动，alpha2仅用作验证环境。当前既有目录隔离不需要为本需求新增core改造；准备入口涉及的startup最小新增仍单列复核。初始化与正常实盘共用物理内存/磁盘，资源竞争与文件覆盖是两种不同问题，优先级与分片方案解决前者。
