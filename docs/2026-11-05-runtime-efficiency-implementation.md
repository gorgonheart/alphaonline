# 下一版后半程优化及Arrow联动：本地实施与复核

基线 alphaonline 7177978，分支 `codex/next-runtime-efficiency`；alpha 在 `codex/arrow-demand-publication`。本轮仅本地修改、离线计算；没有部署、重启、修改账户、真实交易或生产清理。既有用户未提交文档保留。

## 落地范围

| 项目 | 本轮实际行为 | 边界 |
|---|---|---|
| P1 执行器JIT | LiveRebRobust40直接调用可缓存数组/标量函数；原模拟jitclass调用同一数学函数 | 死区、97%纯多预算、2.45默认上限、清仓/开仓/翻仓及截断顺序不变；参数显式传入 |
| P2 模拟行情复用 | 同一再择时子策略的state0/state1复用同轮Pivot及单位信息 | 不建立全局/跨轮缓存；非再择时策略保留原读取；初始化共享输入路径保持 |

P2/P3目前是局部复用，**不是所有子策略共享一个worker行情缓存，也没有实现提前裁剪全部模拟行情**。增加跨子策略常驻缓存及改变对齐顺序仍需独立成本证据。

## Arrow发布深度修正（用户已确认）

不能直接把上游改成4050。当前交易读取器先取 `max(5000, get_kline_num + min_kline_num + 1)`，完成现货/合约映射预热后才最终保留4050。MODEL服务器profile固定get_kline_num=LIVE_BARS=4050，min_kline_num仍来自账户（未配时使用全局配置）。例如168需要5000，1800需要5851。

真实生产发布器→真实Arrow读取器→原映射函数离线对拍：14060全量发布与按上述需求发布，最终4050结果严格一致。直接4050发布的反例会改变映射。因此“缩短发布”和“保留最终4050交易输入”是不同边界。

配置：

- alphaonline `tools/robust40/initialization_config.py`：`ARROW_DEMAND_ENABLED=False`默认不启用；`ARROW_CONSUMER_NAME=None`默认安装目录名。两安装共享上游且目录同名时，显式配置不同功能性名称，参数不迁出accounts。
- alpha `config.py/config.json`：`arrow_demand_enabled=False`；`arrow_demand_min_rows=None`默认沿用`publish_kline_num`作为未注册消费者下限。原配置0意味着保留全量，不能被一个新消费者悄悄缩短。
- 只有核对所有未注册消费者所需深度后，才显式设置公共下限，例如5000。若还有需要完整历史的消费者，下限必须为0。注册消费者更长的需求会继续上调；任一全量请求优先。
- 没有任何注册请求时仍按原publish_kline_num发布，避免新协议自行改变老行为。协议只适用同机共享市场目录。

请求放在 `preprocess_1h_resample/<offset>/.arrow-demand/<安装名编码>/<账户名编码>.json`，只含版本、行数、来源目录和轮次戳。每个消费者一份JSON、一份OS锁，原子写期间至多一份tmp，不保存行情。读改写均持同一OS锁；旧stamp不能覆盖新请求；同值重试会清掉自己的残留tmp。发布器每offset开始只读一次小控制目录，同一深度交给spot/swap两个任务；已发布同stamp不重写。

初始化失败保留全量意图；只有compute校验并安装成功后通知。正常调度核查有效snapshot时可补发丢失的成功通知，使用snapshot实际截止对应轮次。成功通知写失败不使有效snapshot失效；请求锁竞争只延后当前账户。未知/损坏请求、未完成tmp均保守保留全量。

故障维护：损坏JSON不能静默认领或删除其他安装请求，日志会提示；先确认所有者、账户任务退出，再人工修复该小文件。停用账户的全量请求无TTL自动释放，需确认账户不再依赖后人工撤销；此代价是可能多发全量，而非缺历史。请求不是test产物，不能随测试清理删除。

## 数值与性能证据

P1采用冻结7177978数学实现作为独立oracle，不更新golden。覆盖随机持仓、空数组、非连续价格数组、参数变化、死区边界、开清翻仓、输入不变；实际模拟器跨新进程缓存测试沿用。两个全新本地进程：首次调用约11.148秒，第二个进程命中缓存约0.401秒，输出一致。口径为构造+目标手数调用，不含解释器导入，不是整个交易轮耗时；首次编译仍然存在。尚无本版Ubuntu实测，不能把原审计的13秒直接声称为线上已节省。

P2/P3用实际calc_equity两条路径对照：5m/25m普通续算、45m传统lookback=3；首次78小时再续两轮。完整资金曲线、state0/state1及spot/swap比例精确相同。mock合同还证明两次模拟共用输入且不重读刚写的account_state0.pkl。初始化和回放既有共享入口仍需在受影响回归中核查，不把短合成样本冒充所有实盘情形。

补充本地合成成本对照：两市场各14050×256×4字段，32币种选币，先构建相同78小时状态再续一小时。顺序old→new→new→old，阶段耗时旧0.4595/0.4596秒，新0.3338/0.3546秒；行情读4次→2次，读盘0.273/0.275秒→0.154/0.149秒。5ms采样的进程RSS峰值旧401.3～401.5MiB、新430.1～430.2MiB，约增加29MiB。第二对完整进程（包含导入、相同基线创建、报告/PKL读写和续算）旧6.537秒、新6.287秒；不能把局部约25%改善当成整轮25%。测试输入生成单独花6.75秒、写230434792字节，是两路共用fixture成本，未藏入性能收益。12份输出（含模拟器各字段和snapshot_queue）逐项精确一致；峰值为本机RSS，不能直接外推Linux cgroup的文件缓存/swap峰值。原始日志及小结果在test/retiming-benchmark-*.log和parity.json，约220MiB原始合成输入验证后释放。

资金曲线CSV→内存旁路没有启用：14050行合成曲线的CSV写读可造成3022个float尾数变化，最大4.440892098500626e-16。即使微小，也不应在严格一致目标下直接改变仓管输入。

P4使用现有dry_run/none模拟交易路由测试，不访问交易所。统计不覆盖真实订单网络耗时、不验证成交；后续正式运行才有实测样本。

## 写盘与缓存专项

- JIT产生可再生Numba缓存，生产须放正常可写代码缓存/运行缓存目录，不能指向test；版本、Python/Numba及CPU环境不同会重新编译。首次启动允许冷编译，失效后不要承诺热启动耗时。旧版本编译文件可能残留，部署清理应在无在途worker时按旧版本缓存目录处理，不能删除有效snapshot代替。
- Arrow控制文件有界，没有追加台账或每小时备份；tmp只清理当前锁持有者自己的文件。已发布Arrow/冻结硬链接沿用上版生命周期。
- verify完成后先移动主日志到test/logs，再删除当前verify目录；最近24份。删除失败只警告，不覆盖测试返回码。强制中断或prepare_run尚未完成时可能留下verify目录，人工删除test仍安全；不因文件年龄猜测任务是否结束。
- 没新增全行情副本、全snapshot采集、哈希清单或永久研究目录。所有本地测试产物在test内；业务无需它们。
