# 全长度 Arrow 与初始化分批计算（本地待人工复核）

## 实现与边界

alpha 原本就在完整保留历史上计算三个长因子，随后只把末5000根写入Arrow。本次改为 `publish_kline_num=0` 表示发布完整保留历史，正数仍表示末N根。不另建一份行情，不增加重算请求文件，不改变原始PKL、Pivot、同轮四ready、原子发布或保留两个Arrow版本的规则。发布器逐币转换并立即写入，避免额外驻留整个市场的Arrow batch列表。机器 `config.json` 如果覆盖此项，部署时也必须为0。

自动初始化使用 `arrow_full_strict`：冻结同一时间戳的完整Arrow，保留现有原始PKL/Pivot冻结供仓管和子策略模拟使用。同盘仍是硬链接；源端原子替换/清理不影响已冻结的文件。读取schema的 `full_history` 标识和必要列，缺文件、截断版本或缺预计算列均报错，不退回长因子补算。实际历史覆盖/S3日期仍沿用原来的检查。

`tools/streaming_factors.py` 负责通用分批流程：按币种顺序读取/整理，每16币暂存一个PKL批次；时序计算复用一个spawn进程池，每币一次计算所需短周期因子，长因子直接使用Arrow列；每批按原顺序拼接，向各因子Parquet增量写入。该批结果写完即删除该工作区内可再生的PKL中间批，完整Arrow冻结件仍保留。不会生成约2.9GB的 `all_candle_df_list.pkl` 或汇总全市场因子矩阵。计算失败不发布最终Parquet、不安装snapshot；重试按现有独立工作区规则处理。

Parquet浮点列用plain编码，按当前框架的122880行统一row group边界；跨币种批次至多保留一个未满的row group，不按16币边界制造错开的列块。用户明确否决每组合回收worker的耗时取舍，现已删除该生命周期配置及core/backtest新增参数，初始化和续算均保留此前的进程池复用。MODEL_JOB_NUM、既有资源准入和阶段并发上限不变。

正常续算仍 `arrow_strict`，传统账户仍走原配置模式。普通Arrow读取在转Pandas前先截取5000根，随后按原规则对齐并裁到4050；请求更大窗口的账户取 `max(5000, get_kline_num+min_kline_num+1)`。手工PKL预热和历史回退仍保留原能力。本次不修改因子公式、S3日期、仓管参数、回放/季度训练、交易流程或账户配置。

全长度发布增加磁盘和写盘量，两个版本仍持续轮换，不无限累计；初始化硬链接会延长对应文件存活时间。需按实际启用offset数量核算空间，不能直接用原5000深度容量估计。Linux mmap页缓存可回收，但Windows树RSS含映射页，与cgroup memory.current/工作集不是同一口径。忙时2GiB仍是资源目标，不能仅以分批代码宣布达到。

同一真实15m发布：原5000 Arrow两市场1,465,986,276字节（1.365GiB），完整Arrow为3,372,728,772字节（3.141GiB）。按11个offset、各保留两轮线性估计，总Arrow约69.10GiB，相比原约30.04GiB多 **39.07GiB**；不是对每个offset逐一测量。还须预留发布中的临时文件、初始化工作区和snapshot。未修改保留数量，也未删除上游历史。正式成功初始化仍按原规则清理其专属工作区；失败工作区按原规则保留排错。

### 真实历史数值对拍

使用前轮同一15m完整冻结原始行情、公开市场规则及账户参数，生成生产者C长因子+完整Arrow，初始化从空状态开始。fixture生成44.871秒属于测试准备，不计入消费者耗时；生产正常发布原本就计算这些因子。窗口2025-05-09 00:15至2026-11-01 12:15，S3起点2025-04-30 00:15，1025币帧/11627074行。

- 90份Parquet中79份逐值相同，其余11份均为长因子；短因子、截面输出和公共K线无差异。
- 58份子策略持仓/账户产物、完整 `model/state.pkl`、完整S3状态逐值相同。实验回收进程版本的14个组合/43个子策略重新选币、按原顺序和共同起点合并后，也与原保存结果逐值相同；回收方案随后按用户要求撤回。
- 不声称长因子全部满足1e-10：CciV3_10248有109/11627074个值超出原 `rtol=atol=1e-10`，最大失败差1.181824274e-7（SOLVUSDT合约，2025-03-25 08:15）；CciV3_5208有1个值超出，失败点差7.785070366e-10（RADUSDT现货，2025-03-25 04:15）。其他非逐位相同长因子满足既有容差。没有放宽容差或修改golden/因子公式。
- 这些差异来自采用生产者C结果代替旧初始化Python重算。本样本选币/仓管未受影响，不保证不同账户参数/未来阈值临界点都不受影响；如需因子级严格验收，需另修生产者数值实现，不能伪称已经通过。

同一Windows20逻辑CPU/64GB主机，计算进程树绑定4逻辑CPU、Windows Job提交内存上限8GiB，原生库单线程。没有注入忙闲等待；少量专项测试同机执行，缓存/Numba热度不同，不能作为Ubuntu承诺或精确P95。

曾测试每组合回收进程：真实14组合选币296.047秒，树RSS峰值4933.63MiB（4.82GiB），Windows提交峰值5762.95MiB；结果完全一致。但用户认为增加约116秒不值得，**该方案已撤回，不是当前配置**。当前保留统一row group及复用池，对应单项实测183.922秒/6738.63MiB（6.58GiB）；不能沿用4.82GiB作为现行峰值。只恢复添加前代码和删除工具配置，无其他框架功能取消。撤回后仅运行最相关配置/池参数5项检查，全部通过，没有再次运行高内存实验。

首轮输入/时序树RSS约2225MiB，原始映射页包含在内；截面仍约5151MiB（5.03GiB），模型阶段约3836MiB。当前row-group写盘经大/小样本原路径对照，完整数据做了等值重编码和真实下游选币验证；写盘耗时/全阶段峰值未重新测量。选币恢复约6.58GiB后，忙时2GiB、独占4.5GiB及Linux5GiB硬限制 **仍未整轮验收通过**。后续应优先减少选币/截面常驻列和重复大表，而非恢复用户已否决的逐组合进程回收。
