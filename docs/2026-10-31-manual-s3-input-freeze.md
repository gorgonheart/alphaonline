## 唯一日期配置与实际生效时刻

维护账户 S3 原有第四个参数即可，无第二份初始化日期配置：

```python
'filter_list': [
    ('VolumeMaxBias_进出场阈值分离官方', (720, 0.1, 0.9, '2026-08-01'), 'val:==1', False),
]
```

该值是 **UTC 日期**。MODEL 适配层规范化为该日 `00:offset`，使用无冒号的基本时间格式生成缓存键，初始化和实盘相同。当前保留账户手工值，没有擅自改回旧的 2025 年起点：

| 账户 | 当前实际 S3 起点（UTC） | 香港/北京时间 |
| --- | --- | --- |
| 20m | 2026-08-01 00:20 | 2026-08-01 08:20 |
| 40m | 2026-08-01 00:40 | 2026-08-01 08:40 |
| 55m | 2026-08-01 00:55 | 2026-08-01 08:55 |

日期也可写为正确的 `00:offset` 时间；非零小时、错误 offset、非法日期直接报错，不静默修正。一个 MODEL 账户内多个 S3 定义要求日期相同。其他策略的 section 调用不经过此适配，维持原行为。

**行为变化需要审核：** 过去配置虽然写 2026-08-01，但自动初始化曾覆盖为 2025 年 4 月。现在 2026-08-01 真正生效，S3 初始选币和其后持仓路径会改变；不能把旧包与新日期混用，也不能声称新结果与旧策略相同。想维持旧策略，应人工选择旧实际日期，并确认完整历史仍覆盖；本轮不替用户作出该选择。日期越晚，S3 有效历史越短；整个 MODEL 的训练资格仍按其实际观测和既有季度规则决定，不靠修改日期保证。

## S3 日期速算法

统一按 UTC 计算，offset 的小时 K 线并不是 5 分钟 K 线。

定义：

- `R`：本轮 ready 对应的整小时 offset 时刻；最后已闭合 K 线的起始时间为 `R - 1小时`。
- `L`：参与覆盖检查的长历史币中，最晚的原始历史起点；当前仅取长度至少 14000 的币，避免把新上市短历史币当作全市场起点。
- `n`：S3 参数，当前 720；`m`：框架 `min_kline_num`，当前 1。
- `T`：实际 S3 起点，必须为 UTC 日期的 `00:offset`。

**精确规则：** `T >= L + (n + m)小时`，且 `T <= R - 1小时`。将右侧向前取整到下一个（含当前）`00:offset`，填入该日日期即可。“向前”指往未来取整，不能截断回当日午夜。

**推荐人工速算（不扫描全市场）：** 当前完整初始化门槛为 14000，使用这个保守下限计算：

```text
E = R - (14000 - 720 - 1)小时
  = R - 13279小时
  = R - 553天7小时

T = 不早于 E 的第一个 UTC 00:offset
配置 = T 的日期部分
```

前提是上游按当前 offset 发布正常连续、去重的小时 K 线，并有达到 14000 的完整历史币。这个公式给出便于人工选择的保守日期；新币自身有短历史是正常情况，不能要求每个币都满 14000 根。最终初始化仍保留原有的长度/覆盖约束，若上游不足 14000，不能靠改日期绕过。

若**已确认**相关长历史币都保留相同完整的 `N` 根，则可使用更早的 `E = R - (N - 721)小时`：

| 已确认的保留长度 | 从 R 减去 | 适用说明 |
| --- | --- | --- |
| 14000 | 553天7小时 | 推荐保守速算，匹配初始化下限 |
| 14050 | 555天9小时 | 完整 14050 同起点时成立，不能仅凭 BTC 推广到全币池 |
| 14060 | 555天19小时 | 完整 14060 同起点时成立 |

例如 `R = 2026-10-31 02:20 UTC`：按推荐 14000 算法，`E = 2025-04-25 19:20`，填 `2025-04-26`，实际起点为 `2025-04-26 00:20 UTC`。按完整 14050 算法会得到 `2025-04-24`，但它可能不被只有 14000 多根的币覆盖。因此推荐前者，或使用外部工具提供的真实 `L` 精确计算。此例是算法演示，没有自动写入账户。

本地实际 `D:/alpha/config.py` 的 spot/swap 当前均为 **14060**，该目录无 `config.json` 覆盖；用户所述 14050 是本次分析的目标条件，未擅自修改 alpha。Arrow 发布深度是 5000，alphaonline 续算取 4050，这三个数字职责不同。上面的推荐公式仍适用。

人工使用表格软件时，可按日期时间数值计算：`E = R - 13279/24`；`D = CEILING(E - offset/1440, 1)`，填日期 `D`。R 必须先换成 UTC，参数变更后应重算公式中的 720 和 1。

## 滚动清理是否影响持续计算

**状态完整且续算缺口在允许范围内时，不影响 S3 持续计算，不需要每日或每月更新日期。** S3 snapshot 保存当前持仓 `held`、延迟排名队列 `ranks`（720 % 11 = 5 个有效截面）、初始化标志、截止时间和最近 4050 小时的输出。新轮只推进截止时间之后的截面；4050 根用于重算新截面所需的 720 窗口基础因子，不需要回到 S3 原始起点。

已核查上游 `resample_candle.py` / `candle_manager.py` 通过 tail(N) 滚动裁剪并发布。早期 K 线被裁掉、旧 Arrow 轮次被清理，不会清掉 alphaonline 的 S3/仓管状态。后续轮次使用最新同轮数据；如果需要重跑的特定旧 Arrow 已不存在，仍按现有调度等待/重建规则处理，不能假设历史 Arrow 永久可用。

本轮离线构造 16000 小时序列，先以 14050 初始化，再以最多 240 小时缺口、14050 上游窗口和 4050 消费窗口推进，直到上游最早数据晚于原 S3 起点。20/40/55m 的 9 次续算共比较 **437400 个标记**，与完整历史结果逐值一致；同样窗口丢弃 state 后全量重算正确报历史不足。另有独立持仓 oracle 验证全部 0/5/…/55m、空截面、延迟队列、重复截止及并列排名。

这只证明 S3 的滚动状态机制；不等于所有长依赖因子都能从任意 4050 裁剪重算。原来的 CCI2600 → TopK 5366 根约束没有修改，仍须按之前决定调参验证；没有用 S3 通过来绕过它。

## 什么时候需要人工更新日期

**先判断是否必须全量重建，再判断历史覆盖，不能看到日期早于当前数据就更新。**

| 典型场景 | 是否改 S3 日期 | 操作依据 |
| --- | --- | --- |
| 正常滚动清理，state 完整 | 不改 | 固定起点继续推进状态 |
| 重启，完整 state 保留且配置一致 | 不改 | 原有 inspect 判断 ready；clean_start 的保留逻辑本轮未改 |
| 停机 7 小时，所有状态一致、缺口在允许容量内 | 不改 | 使用已有状态补算；7 小时本身不是改日期理由 |
| 损坏、丢失状态；或配置/模拟单位改变，触发完整重建 | 先检查，不一定改 | 若 `L + n + m <= T`，保留原日期重算 |
| 旧 state 丢失，历史已不能覆盖 `T - n - m` | 需要人工决策 | 恢复同口径旧状态或更早行情以保留原策略；接受新基准才改日期并完整重建 |
| 新增一个 5m offset，没有独立 state | 检查该 offset | 能覆盖共同日期就用共同日期；否则补历史或为该 offset 明确设新日期，不能复制别的 offset 状态 |
| 人工修改 n / min_kline_num / 策略参数 | 重新验证 | 日期可保留则保留；参数变化仍按配置规则重建 |
| 想主动重新选择 S3 初始持仓 | 改日期并重建 | 这是策略变化，先回测验收，不是例行维护 |

可在计划重建前用速算法检查：如果配置日期 `T` 已早于新算出的保守 `E`，用真实 `L` 确认是否仍覆盖。理论完整 N 根下，原日期最迟可从头重算的轮次约为 `R <= T + (N - n - m)小时`；这只是**重建覆盖期限，不是运行中 state 的有效期**。无需为它增加每日全市场检查。

## 硬链接边界与性能

仅链接已审计由 CandleFileManager 删除旧路径再创建的预处理 batch/pivot、exginfo、当前 offset BTC PKL、市值 PKL。源文件下次替换或清理时，工作区仍保留旧文件内容；只读计算完成后沿用原成功清理流程释放链接。禁止在冻结目录对链接目标原地写入；不要把此方式扩展到 TSManager 基础分区，它有原地 to_pickle 写入。

BTC 只冻结根目录 CSV（普通复制）及当前 offset 的两种 BTC PKL 文件名，保留 loader 的全部回退顺序；不复制其他币和其他 offset。市值保留所有符号/历史别名 PKL，不按最终选币缩小，不复制无消费者的 ready/CSV。未知 loader 仍复制其原有文件。

同盘支持硬链接时不复制大文件内容；跨盘/明确不支持硬链接时才复制，已有目标或其他错误直接失败，不覆盖可能指向公共数据的链接。已有同轮 ready、冻结前后文件属性检测保留，文件号取自同一次 stat，避免相同大小/mtime 的替换漏检。没有新增哈希、注册表或每轮全历史检测；这些文件检查只在初始化输入冻结执行。

这不是永久零占用：上游发布新文件后，冻结链接仍占住旧数据块，直到初始化工作区释放。并发发布导致版本不一致会沿原流程失败重试，不用 symlink/junction 跟随变化中的公共路径。

离线 32 文件合计 64 MiB、3 次测量中位：普通 copy2 **543.74ms**，硬链接 **23.85ms**；只衡量文件冻结，不代表整轮初始化或生产磁盘保证。主输入测试断言大 PKL 内容复制次数为 0，仅复制四个小 ready 文件；日期准备测试禁止 read_pickle，确认没有隐藏的全历史预读。
