## 业务边界

### 测试 25m：为什么会报 7 天前的修订

以 **19:25 HKT 首次自然 ready** 的 Arrow/Pivot 和消费端事前真正保存的 `revision_inputs.pkl` 比较，旧新各 1,275 组输入；沿用正式比较器的时区、空值、旧快照缺 `funding_fee` 列的兼容规则。各组最早差异如下（香港时间）：

| 字段 | 最早变化的 K 线 | 实查 |
| --- | --- | --- |
| `first_candle_time` | 10 月 29 日 18:25，正好是旧快照最左一行 | 305 个现货、306 个合约的历史起点变化，共 102,648 个单元。示例 1000CATUSDT 现货旧起点为 2025-03-29 20:25，新起点为 22:25。该时刻无价量或资金费差异。不能据此推算窗口外最早变化。 |
| 已保存的合约 Pivot 资金费 | 11 月 4 日 18:25 | 1,058 个币/小时变化，HOTUSDT −0.00045378 → −0.00055112。 |
| 合约收盘价/高低价/量等 | 11 月 5 日 16:25 | 1000PEPEUSDT 收盘 0.0049833 → 0.0049851，成交量 3,579,350,127 → 3,579,948,098，成交笔数 79,452 → 79,508。 |
| 现货收盘价/量等 | 11 月 5 日 17:25 | BNBUSDT 现货收盘 716.47 → 716.48，成交量 2,248.934 → 2,248.978。 |

正常增量沿用旧批次的历史起点；常规冷启动清理派生缓存并重建，在新可用的行情窗口重新求最早 K 线，再把这个起点填到整段历史。因此两个 168 小时快照从首行起就不同。该字段还用于选币预热和 MODEL 的 `age_days`，不能直接屏蔽。过去一日并非从未检出：测试 14:25、17:25（本次资金费发布前）分别报过 10 月 29 日 11:25 和 16:25 的修订并要求重建；18:25 则是正常续算。这里只确认旧日志所报日期，不推定旧两轮逐格差异原因相同。

资金费合并只处理费用列；普通增量保留已缓存的历史价量，冷启动从基础 K 线重新采样。另对上述两个真实币各独立读取交易所已闭合的 12 根 5m K 线；新发布的收盘、成交量、成交额、笔数均匹配。发布前逐笔/原始响应未留样，不能凭这两组结果归责于某个接口或某一笔漏采。测试 19:25 的三份行情资金费一致（ready+92.3 秒），账户因**全部输入**超回放范围而进入既有测试重建流程。测试 15m 自然轮 ready+100.1 秒，同一真实样本 43 行的独立双版本回放一致。逐字段证据保存在测试机独立验证目录内 `1925-input-diff.txt` 和 `1925-binance-closed.txt`。

- 资金费原始数据按合约共享；它不是给某个 offset 已发布的交易数据。每个 offset 只在自己本轮预处理时修正本目录，继续沿用小时对齐（例如 08:00 的资金费对应 25m 数据的 08:25 行）。修正可在不同 offset 的相邻自然轮次先后生效，不要求同一墙钟时刻全部相等。
- 普通实时采集的 exchangeInfo/资金费不再要求启用该分钟。K 线和实时预处理仍照既有偏移运行；原有空档补算仅针对缺失产物，不作为资金费推送机制。禁止为此次修正唤醒其他 offset、伪造 ready、修改已交付轮次或重复请求消费者。
- 批次、当轮 Arrow 或已有的 PKL 回退、年度 Pivot 一致后才给本市场公共 dict ready。传统启动门实际只看 spot/swap 两个 dict ready；不能用固定休眠假定 Pivot 已完成。MODEL 沿用其四个标记。消费者下一小时读一次新轮数据，即可看到此次纠正。
- 模型的原始 K 线列为 funding_fee，Pivot 列为 funding_rate。旧 MODEL 修订快照若没记录原始列，首次加载不会因增加字段追溯整窗；原已记录的 Pivot、价格等仍可触发实际回放。传统账户仍按既有续算窗口工作（默认 0）：**发布历史已修正不等于已经成交的订单或窗口外的历史模拟资金曲线被改写**。
- 资金费修正后结果可以与旧版本不同。验收比较的是两套**已修复**候选在相同输入、相同 offset、相同逻辑轮次下的结果；用独立的结算数值校验，不能只证明两个版本同错。真实交易所的结算与账户扣款不是同一数据源，本次不对账私有成交。

**先在测试机验证 B + A 影子，再单独放行正式机。** 两套数据中心不可对同一个目录双写，同一出口也不需启动两个实时采集器做对照。

1. **发布前盘点。** 核对两台机器的 PM2 命令、cwd、解释器、storage_path、消费端 bmac_data_path、有效 offset/发布深度/资金费开关及账号运行模式。对应文件做窄范围源码差异检查；非 Git 安装在隔离副本套用补丁，冲突须人工核对，绝不覆盖整文件恢复上游默认。私有覆盖配置和在测功能不打包。备份变更前源码、当前配置和启动参数；确认有足够空间与重启窗口。
2. **准备维护窗口。** 行情生产者重启必经 init_history/init_dirs，会重建交易对、重采样、预处理目录及 ready；基本 K 线与原始资金费目录保留。测试版的 offset 内 .arrow-demand 也在预处理目录，事前保存有效需求；在第一轮依赖短发布前按现有消费者协议重新登记并核对，重建中的账户必须保持全量。不得手工补 ready、删除账户 snapshot 或复用上一轮时间戳。确认无已派发且仍在读旧产物的账户；若无法避开维护缺口，推迟切换。
3. **测试机先行。** 在测试机独立 test 目录，用同样冻结的资金费输入与 K 线分别跑正式候选 A 和实际测试安装的候选 B；禁网、独立 data/log，不能让影子进程发布到消费者目录。通过后只更换测试生产者本次文件，在维护窗口重启该实例。需发布 MODEL 接收补丁时单独按其更新流程加载，保留快照，不更改交易模式，不下单。
4. **自然轮次验收。** 等初始化结束、回补冷却结束、出现至少一条已知修订，并覆盖受测各 offset 的下个自然 ready；再观察一轮无新修订。若没有真实修订，只能报告运行健康，不能记为真实纠错通过。用冻结的相同原始输入/基线缓存和发布时刻驱动 A 影子对账，不能直接对比两台不同时间的交易所响应。检查合约费率、原始 PKL、年度 Pivot、Arrow 共有行/因子列、策略输入；价格、索引、币种、非资金费字段应相等。测试版短 Arrow 仅行数、相应全量标志可按配置不同。若验证交易行为，使用相同账户和同一恢复点、禁单模式，分别对比资金费、模拟权益、选币及目标仓位；超出恢复范围时按各自既有机制恢复，不要求流程和耗时相同。检查小时覆盖、失败/限流、实际 ready 时间和是否错过交易轮。
5. **正式放行。** 仅在测试差异已解释、近期回补覆盖和 ready 延迟可接受后，按已核对的正式实例做相同的窄补丁切换。保留原配置和正式的交易端版本线；不启动备用实例、不切数据路径。首轮及随后各活动 offset 重复上述资金费检查。任何机器的真实发布、启动/重启与交易模式变更均未包含在本次本地实施中。
6. **回退。** 在对应机器维护窗口恢复该机器自己的旧源码/配置与服务命令，不交叉用 A/B 副本；停止新实例后才允许旧实例写同一目录。还原代码不能撤销已确认的交易所结算、已读取的输入或订单：保留原始结算数据与账户状态，按原流程重新生成下一轮派生数据。已处理过修订的 MODEL 状态如果不兼容，应独立验证恢复点并走原有受控重建，不用过期 snapshot 覆盖实际仓位。若费用列不一致、ready 先于 Pivot、其他 offset 被改写、连续轮次缺产物或限流损害行情，应停止放行并留存该轮输入和日志。

## 可复现对拍

生产者仓库的 tests/compare_funding_releases.py 接受两份已合入资金费补丁的源码目录，复制其中 core 到临时区，用空配置、独立进程、合成行情与真实 Arrow/PKL/Pivot 读写。无需联网、生产数据或凭据。运行：

    python -B tests/compare_funding_releases.py <正式候选源码目录> <测试候选源码目录>

本地对拍是生产者业务等价性证据，不是两台机器部署证明；测试机的其他已部署功能及目标 Ubuntu 的实际吞吐、代理额度和正式 PM2 目标仍须按上述步骤核对。

## 离线结果与边界
