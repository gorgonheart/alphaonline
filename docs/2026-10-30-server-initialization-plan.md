# 服务器完整初始化与4050 Arrow续算方案

实施进展：已进入TDD开发及离线验收，实际接口、最小core清单、验证证据与相对本方案的明确取舍见 [实现与人工复核](2026-10-30-server-initialization-review.md)。以下保留原设计，不代表全部已经验收或获部署批准。

日期：2026-10-30。状态：方案修订v2，加入自动重建、轻量检查、S3起点策略和实际磁盘测量，待人工审核与开发；没有修改运行代码、启动服务、删除生产snapshot或下单。

本方案取代双运行v2中“本地初始化后上传服务器”的部署主线。保留单一正常账户配置、独立初始化差异配置、严格一致性、S3截面状态及各offset独立的要求。长依赖优先由后续调参缩短，本轮不新增CCI等预计算因子、不代改参数。

## 1. 运行规则

同一台实盘服务器负责初始化和交易。账户config始终描述正常运行；独立初始化配置在无历史或不能安全续算时生效。按用户最新要求，输入异常、缺少状态、断档超出续算能力可自动触发完整重建。第一次或重新完整计算不是交易回放：只生成计算状态和最新目标，不对历史小时发订单。

| 本账户状态 | 行为 |
|---|---|
| 所有相关历史均不存在 | 在隔离工作目录读取完整140xx历史，构建全部状态，验证成功后安装，再自动进入正常交易准备 |
| 已有完整、配置匹配的snapshot | 读取4050根闭合Arrow，恢复并续算 |
| 有文件但缺S3/子策略/MODEL任一状态，或截止时间不一致 | 自动转完整重建；完整输入可用后，在本账户隔离目录构建，不混合使用残缺旧状态 |
| 配置发生策略语义变更 | 记录具体变更后按已配置的新策略完整重建；相同失败条件不在10秒重试中反复重跑 |
| Arrow缺文件/缺必要列，但同轮完整PKL、pivot和规则数据已就绪 | 自动走完整初始化配置重新计算，成功后恢复正常交易；不能使用4050根现算缺失长因子 |
| 缺失小时超出4050续算能力，完整输入可用 | 自动重建；对S3旧起点是否还能保留，按第8节执行 |
| 数据未ready，完整输入也未就绪/正在写入 | 自动初始化请求等待输入；新一轮完整发布后重试。不删除snapshot、不用陈旧数据发单，因为重新计算不能生成缺失的行情 |

当前 `get_snapshot_time`/`has_snapshot` 只看时间标记，不能作为新方案的完整性判据。按第9节采用“小元数据+必要文件stat+业务读入时顺手校验”，避免每轮重复反序列化全量snapshot。不增加哈希或额外manifest系统，复用现有配置元数据和snapshot时间标记。

允许必要时清理本账户snapshot中的旧数据，但顺序是：确认完整输入可重建 → 锁定账户 → 隔离计算成功并校验 → 替换本账户状态 → 清理旧目录。若空间不足必须先清理，先确认输入可用并明确本轮选择全量重建，再只清理已解析到 `data/snapshot/<本账户>` 的目录；不得触及其他offset、生产者行情或实盘订单记录。首选成功后替换，避免缺数据时先删掉唯一状态。

对同账户、同发布时刻、同失败原因只启动一次初始化；失败后等待新发布或输入/配置发生变化。使用已有协调进程内的任务状态与退避，不新增持久化登记系统。Arrow长期未修复时新轮次可继续走完整计算降级，但须明显报告全量降级和耗时，不宣称4050正常；避免12个offset同时反复全量占满资源。

## 2. 单一账户配置与初始化覆盖

账户配置固定正常模式：4050、严格Arrow、正常调仓/BNB设置、统一的S3初始化日期。单独的初始化配置只覆盖运行输入和资源，不复制strategy_pool、不包含账户凭据。

建议覆盖项（接口草案，尚未实现）：

```python
INITIALIZATION = {
    'history_bars': 14064,
    'source': 'full_pkl',
    'job_num': 2,
}
```

14064是当前讨论的候选，需要与生产者实际完整输入边界统一后定稿；不能把14050/14060/14064视作对所有状态因子天然等价。

允许覆盖：行情读取长度/来源、完整历史覆盖检查、初始化并发数、临时目录。禁止覆盖：选币/因子数学参数、黑白名单、再择时、调仓阈值、手续费、分钟偏移。S3采用账户基准中统一声明的起点策略，初始化时按第8节解析出具体日期并保存；正常4050续算始终复用该日期，不是两套配置分别写不同日期。固定日期模式仍可用，但不保证滚动140xx行情永远能从该日重建。

加载顺序：账户正常配置 → 仅初始化worker叠加初始化覆盖 → 再生成data_config等派生配置。不能在core模块已执行 `from config import ...` 后临时改全局变量。初始化使用独立worker，正常交易用正常配置进程，防止140xx设置泄漏到其他账户/后续轮次。

如果需要修改S3起点策略或长因子参数来达到成熟模型/4050约束，应先修改并审核唯一基准配置，再初始化。完整行情长度不等于模型有效历史长度，仍需报告共同有效起点、完整观测日和季度模型训练情况。

## 3. snapshot保存范围

以 `data/snapshot/<账户+策略>/` 为完整计算状态边界：

```text
snapshot_time.txt          # 本账户完成时刻，成功检查后才作为可用状态
<现有S1...S14目录>/         # ratio、选币、account_state0/1、lots_state0/1等
section_state/            # 显式支持续算的截面因子状态，首先是S3
model/                    # MODEL context/result、模型、虚拟账户及待续算状态
<公开计算配置元数据>        # 复用已有配置记录，保存本次实际计算定义
```

这是逻辑布局草案，开发时优先沿用现有文件名，避免重复存储相同数据。账户/offset/因子参数各自隔离，不以offset alone混用不同账户。

“全部放snapshot”指恢复计算需要的完整状态，不是把生产者原始PKL、所有Arrow、全部临时因子缓存永久复制进去。初始化可冻结一轮完整行情供计算，完成后按既有缓存管理规则处理；正常运行仍从alpha读取新行情、pivot和市场规则。MODEL需要的历史价格/观察样本等保留在其状态中，不裁成4050。

S3必须保存截面完整持仓标记和时间，不能拿最终选币结果代替。通过既有df_prev恢复T的持仓，结合基础VolumeMaxBias窗口与延迟排名缓冲，只推进T之后的小时。无有效前态不得在4050根上重走2025年初始化。

## 4. 现有实现必须处理的冲突

### 启动清理

`startup.py` 默认clean_start=True会删除整个snapshot目录。现在的预热保护仅针对配置warmup_path的账户，不能满足新方案自动持久化。

对显式采用本方案的账户，正常重启必须保留并轻量校验其完整snapshot；旧账户保留原清理语义。优先按账户保护/清理，取消新模式下“每次复制整套状态→删除→复制回来”的工作，不得全局设clean_start=False来解决。完整重建由本账户实际异常触发，不复用普通重启开关。

当前 `warmup.prepare_startup` 还禁止MODEL state位于snapshot，并要求外部包；这些规则需对新模式调整。既有 `data/robust40_state` 与外部包仅保留兼容读取/明确迁移路径，不能自动把旧state搬进不匹配的snapshot。当前活动旧包与配置有差异，不应直接搬迁。

### 首次MODEL计算不能依赖已有bootstrap

`live.prepare` 在计算前读取state或bootstrap；rebuild工具也读取旧bootstrap中的虚拟手数单位。因此“没有历史”时直接跑当前流程仍会失败。

需增加真正无bootstrap的初始化分支：从同轮冻结的市场规则建立初始虚拟手数单位，使用现有 `calculate` 计算完整MODEL；以后由 `advance` 续算并保留既有单位。子策略模拟状态也须一致恢复。初始化完成不再依赖旧研究包。

### 4050依赖及输入

初始化长历史不会消除后续长依赖：目前CCI过滤2600→TopK仍超4050。按用户决定通过参数验证缩短，不新增预计算；在新参数验证通过之前，严格4050模式不能宣布可上线。其余既有长预计算因子仍由alpha完整计算后裁Arrow，生产者不能也缩为4050。

完整输入与Arrow必须同数据口径。raw特征读取同轮未过滤行情，保留BTC、first_candle_time及所需成交/费率字段；MODEL以共同尾部构造incoming，追加到完整旧state，不能要求短pivot覆盖全部历史净值。现有pivot/exginfo链路继续保留。

### 状态成功与交易成功分开

当前child模拟会先写snapshot及时间标记，之后MODEL才计算；一个文件存在不代表整轮成功。新增截面状态也必须纳入同一计算完成边界。

初始化在隔离目录完成并验证后安装；正常续算保留上一份完整状态对，对当前多文件写入失败提供恢复。不能把逐文件replace描述为整套状态原子提交。目录切换/备份恢复需要测试进程中断点，不引入额外哈希登记。

计算完成但下单失败时，保留计算结果；重试重新查询真实余额、持仓及订单状态，不重新初始化，不重复发送上一轮差额。计算snapshot不应被当作交易所持仓或订单执行凭证。

## 5. 首轮自动进入交易的时序

推荐在startup分发账户子进程前，由账户初始化协调器检查/准备状态，而不是在 `real_trading.prepare_live` 才启动长时间初始化。后者太晚：当前account_exec已更新账户并可能补BNB，real_trading已撤单。

1. 只处理到达该offset且数据ready的账户，检查snapshot完整性并防止同账户双写。
2. 无历史则冻结一轮完整输入，在隔离worker完成14子策略、S3截面、模拟和MODEL初始化，写入配对snapshot。
3. 核对计算截止时间与当前已闭合行情。若仍在该账户允许的当轮执行窗口，进入正常交易准备；正常4050路径必须支持同根不重复推进状态。
4. 若初始化耗时跨过执行窗口，不沿用旧run_time发单；自动在该账户下一可执行offset使用最新同轮行情续算、补齐缺失小时，只生成最新目标，无需用户手工重建。
5. 长初始化完成后重新读取账户资产、持仓、市场规则及价格，按原BNB设置和正常交易流程执行。不能沿用初始化开始前的账户快照。

第一版可以先完整初始化一次，再进入正常4050流程进行首次衔接验证；不为了省一次短窗计算新增“跳过整个backtest”的隐式分支。后续若复用初始化当轮产物，必须显式证明同一run_time、配置与输入且状态未重复推进，再单独优化。

“完成正常下单流程”可以做到自动衔接，但不能保证完整历史计算无论花多久都在第一次触发点立即发单。执行窗口必须明确，与现有数据ready等待上限不是同一个概念；窗口过期后应自动等待合适的下一轮，而不是交易陈旧信号。

全12offset场景下，冷启动串行可能耗时很久并阻塞其他已就绪账户。初始化队列与正常交易分发需分离：未就绪账户只计算，已就绪账户继续正常调度；初始化worker使用独立目录和受限并发，不能和正常交易争用共享cache/runtime。首版可支持按offset依次启用，不在一次启动时并发12次全量计算。

## 8. S3日期最优方案及实际等效起点

建议：**按140xx完整历史确定初始化起点；一次成功初始化后固定下来，4050续算不移动起点。** 为支持未来自动全量重建，采用“优先保存的起点；无法覆盖时按完整历史重新确定”的统一策略，而不是账户写一个不断更新的近期日期。

定义：E是本轮已闭合尾根；R是本轮完整输入在稳定老币上的合格共同起点（不是年轻币最晚上市时间）；S是S3实际首次生效时间；T是已完成snapshot尾根。

- 首次无历史：从完整数据确定R，给VolumeMaxBias(720)保留至少720小时预热；将R+720h向后对齐到offset日界00:mm，得到S。还需核对上市过滤、数据缺口及可用市场截面，不能只用一个币的最早行判定整个币池合格。
- 正常续算：S不变，只推进T+1h至E；4050输入通常从E−4049h开始，但它不是策略初始化起点。
- 自动重建：若现存元数据中的S仍有足够的前置历史，优先保留S重算；否则按新完整输入计算S_new并保存新基准，日志明确列出旧/新起点。正常配置和初始化worker均由同一起点策略解析，实际strategy_pool和保存基准必须使用同一个解析结果。
- 原section继续接收实际时间字符串，不要求它识别auto；解析放在策略配置/工具适配层，core不认识S3日期。

本次40m实读：完整BTC原始行情14064根，2025-03-23 08:40至2026-10-30 07:40 UTC；四类共同ready为08:40，对应闭合尾根07:40。按以上规则，该样本候选S为 **2025-04-23 00:40 UTC**。4050行情窗口起点为 **2026-05-14 14:40 UTC**，续算后S3的历史起点仍是2025-04-23 00:40，而不是2026-05-14。具体S需全币池与该offset初始化验证后确定，不能直接把40m候选平移当成其他offset验收结果。

如果保持现配置2026-08-01，则实际S3历史仍从2026-08-01开始，读取14064不会自动变成2025年策略。当前已保存child S3约2163小时，而不少其他child已有约1.4万小时；父模型共同有效历史仍受S3及后续因子预热制约。

边界：**仅保留滚动140xx行情、允许自动完整重建、又要求永远与最初2025年不中断续算完全相同，这三项不能无条件同时满足。** S3路径依赖、模型训练样本及虚拟账户状态会在重建时重新形成。最优实际方案是完整状态可用时始终续算；确需重建时保留旧S能保留的部分，否则明确建立新基准。若将来要求跨任何重建也完全等价，需长期保存原始初始化历史及相关输入，不能靠4050/140xx两个窗口解决。

## 9. 高效简单的状态检查

不在每轮启动调用当前 `validate_snapshot` 扫描全量ratio/account、反复加载MODEL或复制整个目录。

快速路径仅做：

1. 读取一份小型配置元数据（沿用warmup.pkl的用途/字段，不新建哈希登记）：账户、offset、有效计算配置、S3实际起点、共同截止时间、完成状态。
2. 按14个child及启用的state0/state1列出固定必需文件，检查存在且非空；检查S3及MODEL状态文件。只stat，不递归读取内容。
3. 比较元数据和snapshot_time、当前UTC闭合根；检查缺失小时是否落在实际输入/因子依赖覆盖范围内。
4. 正常业务本来就会读入ratio、模拟器和MODEL，在这些已加载对象上顺手检查实际截止时间/轴/参数，不增加第二次读盘。真正的历史一致性仍由已有merge_context等检查完成。

写入方先将同一元数据标为未完成，所有计算状态成功后最后更新为完成；写小元数据用临时文件替换。不能仅凭小元数据声称已验证任意文件内容；内容损坏在业务首次读取时转自动重建。初始化/安装时做一次完整配对验证，常规入口不重复深检。

约百次以内或数量级相近的stat和一份KB级配置读取是设计目标，实际文件数按child配置计算；不承诺未经实测的毫秒数。验证时测冷/热磁盘入口耗时，并断言快检不加载大ratio/MODEL文件。额外的完整历史数值校验不因快检而放宽。
