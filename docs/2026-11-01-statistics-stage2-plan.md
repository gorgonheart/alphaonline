## 第二阶段目标及推荐顺序

建议先做2A/2B，恢复可信的增量成交和现货成本；完整账户收益归因放2C。当前价格影响报告继续独立存在，不直接改名为真实盈亏。

| 子阶段 | 交付 | 必须解决的问题 |
| --- | --- | --- |
| 2A 原始成交增量 | 原始成交、ID去重、可恢复游标和明确采集状态 | 满页、同毫秒成交、重复、迟到、接口失败、跨账户/钱包身份 |
| 2B 剩余成本与对账 | 可信期初支持下的剩余成本/均价、已实现及未实现盈亏 | 手续费资产、部分卖出、清仓后重开、划转缺口、账实一致 |
| 2C 实际期间收益 | 完整现金流支持下的账户收益与归因 | 外部出入金、内部划转、资金费、利息、币种折算、借贷负债 |
| 2D 验证与接入 | 回归、性能计数、故障恢复、人工复核项 | 独立oracle，不用新golden掩盖旧账错误 |

### 1. 原始事件与账户身份

保留UTC毫秒时间、原始trade/fill ID、order ID、交易所、交易所账户标识、钱包类型、原始instrument、方向、量价、成交额、手续费原币金额及资产。API原始十进制字符串保留，计算时才按明确精度转换；不能先round到小时、取手续费绝对值或丢失ID。

唯一键使用交易所/账户/钱包/instrument/成交ID组合，不使用小时分组、仅时间或单独trade ID。ID不连续不等于漏单，不能靠ID差值推断缺口。新增策略归属依赖订单ID与本地下单回执的关联，不按成交分钟猜offset。

11个offset如果使用11个独立交易所账户，则状态分别保存；如果共享同一交易所钱包，钱包余额/成本是账户级事实，不能简单拆成11份独立持仓。共享钱包的策略成交归属需要订单映射；没有映射则只展示账户级结果。这一项在接入前核对现有账户关系，不读取/打印凭据作报告。

### 2. 严格分页与错误语义

新增统计专用只读分页接口，例如`fetch_trade_page(wallet, instrument, cursor, begin_ms, end_ms, budget)`；返回原始rows、下一游标、覆盖区间及完成状态，失败抛出明确错误。成功且无成交、历史不可访问、触发预算而尚未取完、网络失败分别处理，禁止用空DataFrame统称成功。

当前本地代码已经证明不能直接恢复旧路径：

- Binance base_client.fetch_spot_trades丢弃id/orderId，失败返回空表。StandardClient选用普通现货myTrades，而PortfolioMarginClient选用杠杆myTrades；不能只验普通现货。
- OKX旧函数只取100条，把费用取abs，并丢失成交ID；旧statistics.get_orders却以1000条判断是否还有页，两者不能匹配。
- statistics.orders先将成交时间移到offset小时，分页再删除“最老分组”；满页同分组会出错，同小时晚成交还会被旧账本过滤。

推荐每轮只查询本轮订单涉及的币种、现有持仓及已有未完成游标。已知范围内定期小重叠窗口补查，用原始ID去重。固定小时交易报表按订单回执run_time归属；手动交易按实际时间区间分组并注明来源。采集截止以实际observed_at为准，不能把迟到执行的23:20轮成交错误截在23:20。

交易所分页分别实现：Binance按各钱包接口允许的fromId或时间窗组合推进；OKX按对应端点的billId方向推进。禁止把fromId和不支持的时间参数混用，不假定满页长度或游标方向相同。[Binance现货规则](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/rest-api/account)、[Binance杠杆规则](https://developers.binance.com/en/docs/catalog/core-trading-margin-trading/api/rest-api/trade)、[OKX成交历史规则](https://www.okx.com/docs-v5/en/#order-book-trading-trade-get-transaction-details-last-3-months)。

币种集合完整性必须单独声明：只查本地订单/当前持仓不能发现未知币种上已买入再卖出的手动交易。全账户历史完整性要靠可信导出或显式的离线币种发现；不能一边禁止全市场在线扫描，一边声称覆盖任意手动成交。

### 3. 增量存储与事务

建议标准库SQLite，每交易所账户一份，放在该账户统计目录；不引入外部数据库服务。主要表为原始fills、现金流事件、采集游标/区间、资产成本状态，以及确有需要时的订单映射。账户级单写者，沿用现有统计互斥；成交/现金流ID建立唯一索引，时间和instrument建查询索引。原始数值存字符串以保留来源精度。

一个事务内提交新增事件、对应成本状态和采集进度；数据库提交完成才发布统计结果。进程中断/磁盘满则回滚，下一轮按旧进度重复抓取并去重，不出现“游标已推进但事件未保存”。按批提交而非每条成交提交，不每轮加载整月CSV、重写多年PKL或重算所有资产。

SQLite会新增一份明确的数据来源和schema维护成本，但能直接保证跨事件/游标/成本的一致性；继续用多个CSV/PKL需额外处理跨文件崩溃恢复，并非行数更少就更简单。最终存储方案在开发前人工确认；本轮没有创建该数据库。旧CSV/PKL保留原义，仅作为历史参考，不静默迁移为可信成本。

检测到比已计算时刻更早的新成交时，只回放受影响资产到最近可信小状态；超出保存范围或缺失事件则标记待对账并要求离线修复，不能直接丢弃。原始成交不因市值低于5U删除。

### 4. 成本计算与费用

采用明确的移动加权平均口径，并用手工样本作独立oracle。设现有数量Q、剩余成本C、买卖基础币数量q、成交计价币额v；先限定已验证的报价币/折算范围，其他币对标记不支持或待折算。

- 买入：基础币手续费从到账数量扣除，计价币手续费计入购入成本；新均价=新剩余成本/新到账总量。不能把手续费同时从数量和成交额按比例扣掉。
- 卖出：按实际流出基础币数量分摊剩余成本，卖出净收入扣计价币费用；只从剩余成本剔除对应已卖数量的成本，不用“累计买入额−累计卖出额”充当剩余成本。基础币卖出手续费会额外减少基础币库存。
- 清仓：数量按交易所精度/stepSize与数值容差判定，而非当前价格×数量低于5U。处理完清仓事件后继续处理同批后续重开仓。
- BNB等第三币费用：保留原资产数量变化，使用成交时可信折算价，而非当前ticker回填过去费用；缺折算时保留未知。费用币自身成本处置、主资产费用分摊与账户收益归因分开，防止重复扣费。
- OKX费用扣减与返佣原符号必须保留并在适配层规范成统一正费用/负返佣；不能使用abs。[OKX费用字段定义](https://www.okx.com/docs-v5/en/#order-book-trading-trade-get-transaction-details-last-3-months)。

独立样本：买2币共200U，卖1币得150U且无费用，则余量1、剩余成本100、已实现50；净投入50并不是剩余成本100。完整数量匹配仍不能证明缺失划转和费用已经补齐。

可信期初只接受完整事件支持的已知空仓起点，或明确来源且人工核对的期初数量/成本。当前ETH多出的5.010667数量不能靠重新计算恢复原因；拿实时价格当历史成本会制造新的错误。来源不够时可以先恢复新增成交统计，成本仍待对账。完整清仓后，在事件来源完整且与实时零库存吻合的情况下，可从新周期开始建立可信成本。

### 5. 真实1h/24h收益

账户范围和计价币一致时，期间收益按`期末净权益−期初净权益−期间净外部流入`计算。账户内部钱包搬移不是外部收益，借还本金不能当利润。必须校验两端净权益已经正确包含负债、未实现盈亏和利息；不同客户端不能只凭字段同名就认为等价。

费用、资金费、利息、已实现和未实现变化用于收益解释；已经反映在账户净权益中的费用不能再次从总收益扣掉。非USDT出入金按发生时价值估值，价格缺失则期间收益未知。各来源的已覆盖区间均足够才发布“实际收益”，否则继续展示权益变化/价格影响及缺失项。不要把订单回执当完整fills，也不要把3个月API可取范围当无限历史。

## 性能和可能耗时

### 每轮运行耗时

以下均为工程估算，不是实盘测量。只估第二阶段新增开销，第一阶段基础overview、已开启的图表/通知、Python启动与当前下单后等待另计。

`新增耗时 ≈ 实际分页请求数P × 每页耗时L + 限速等待 + 新增事件处理/提交时间`。无新增成交也可能要查询才能证明无成交；“增量”不等于不请求。Binance通常需要按币种查询，OKX部分接口可按市场批量查询，P不直接等于新增成交条数。

| 场景 | 页数/条件假设 | 新增耗时粗估 |
| --- | --- | --- |
| 只复用已经完整采集的本地结果 | 0请求，小批量索引查询 | 目标10–100ms量级，需实测 |
| 少量活跃币种增量 | 2–5页，L假设0.3–1秒，无重试 | 约1–6秒 |
| 普通/较多币种增量 | 10–30页，同上 | 约3–30秒 |
| 首次补历史 | 100–1000页，同上 | 约0.5–17分钟，限速/导出等待可显著延长 |
| 网络超时/限流 | 非正常场景 | 以统计专用预算终止新增查询，结果标为未完成，下轮续取 |

例如20币每币1页、每页0.5秒，网络约10秒；相同20币各补12页则约120秒，尚未计限速与本地处理。不能承诺整个账户“初始化1秒”。若覆盖多年、许多币种或API历史已不可访问，需要离线导入，可能数十分钟到数小时，等待外部导出另计。

本地成本处理目标：1000条新增事件约10–200ms、1万条约0.1–2秒，均包含小批次落盘的预期量级而非已验证数字；使用Decimal、费用币折算和受影响资产回放会增加成本。实际应以代表性样本基准验收，不把纯数学内核计时当完整统计耗时。

建议独立只读请求timeout初值5秒、最多1次重试、单轮新增采集软预算30秒、全局并发继续小规模并按接口权重调度。预算耗尽不清数据、不推进未完成覆盖、不阻断基础报告。30秒是停止发新请求的软预算，不是无条件30秒硬退出：最后一个在途请求/提交会增加尾部时间。具体代理/连接/读取超时语义要测试后再定。

当前全局timeout=30000ms、retry_times=5、sleep_seconds=5；按每次占满30秒且睡5秒粗算约175秒/接口，尚未计校时等，并非严格总时限。第二阶段不能继续复用这组预算后又宣称“30秒内结束”。只修改统计专用客户端，订单和基础overview先保持现行契约。

11个offset分别运行时，CPU/IO与API总工作量相加；若均匀分布在5分钟间隔通常较少同时触发，但慢任务仍会重叠。当前最多2个统计在途；新增采集与图表需计入同一容量，不另开11个并行历史补拉。初始化/离线补历史以独立低优先级任务执行，普通轮次不等待补完多年历史。

## TDD与人工验收

独立手工oracle覆盖：满1000/100条、同毫秒多fill、重叠分页、重复ID、迟到成交、返佣、基础币/报价币/BNB手续费、部分卖出、清仓后重开、未知划转、共享钱包和不同offset。崩溃点覆盖事件已插入但游标/成本未提交、数据库锁/磁盘满、分页失败、预算终止与下轮恢复。旧客户端调用默认不变，5/15/20/25/45等策略、交易前snapshot及补BNB回归。

验收需分别给出API页数/权重、完整覆盖区间、本地处理/提交时间、峰值内存、缺失事件状态，以及新旧统计与真实账户数量/权益核对；不能只给总测试数量。实现完成后先出core专用diff人工复核，再授权联网单轮验收，不借统计测试下单或重启。
