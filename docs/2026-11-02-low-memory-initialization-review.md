## 性能数据

Windows alpha311、独立进程，合成完整时间轴，含并列排名/连续空截面；包含Polars→Pandas转换、完整S3初始化与25点构建。warmup/JIT单独计时；峰值RSS每10ms采样，包含解释器和基准输入，不是整台机器或完整框架峰值。

| 14050小时×812币种 | 旧实现 | 新Numba路径 |
|---|---:|---:|
| S3阶段耗时 | 49.96s | 21.97s |
| 峰值RSS | 10,518MiB（10.27GiB） | 3,280MiB（3.20GiB） |
| 额外峰值（扣除输入准备后RSS） | 8,755MiB | 1,534MiB |

单样本峰值下降约69%，时间下降约56%。输入有8列无关数值列，对照旧宽表转换与新必要列投影。真实1141万行的行情分布不同，因此不承诺相同耗时或峰值；不是P95。

Ubuntu4c8g隔离、nice19、数值库/Polars单线程，14050小时×128币种，三轮交替新进程：

| 同一优化后数据路径 | Numba | C++候选 |
|---|---:|---:|
| 中位S3阶段耗时 | 4.087s | 4.030s |
| 峰值RSS范围 | 788–791MiB | 757MiB左右 |
| 内核首次调用（单列，不含上述时间） | 0.411–0.497s缓存加载 | 约0.00008s |

三轮所有输出和状态完全相等。C++中位仅快约1.4%，不足以证明值得引入生产二进制维护；当前保留Numba缓存内核，C++作为可复跑候选。Windows相同小规模比较也没有明显C++端到端优势。没有声称所有平台/负载下Numba总是最快。

## 复跑入口

Python仅用alpha311。工具 `tools/benchmarks/s3_memory.py --help` 提供baseline/numba/cpp；baseline必须来自改动前Git源文件，不生成新golden。候选C++在Ubuntu可用：

```bash
g++ -std=c++17 -O2 -ffp-contract=off -fno-fast-math -shared -fPIC \
  tools/benchmarks/s3_kernel_candidate.cpp -o /tmp/s3_candidate.so
S3_BENCH_LIBRARY=/tmp/s3_candidate.so python -m pytest tests/test_s3_native_candidate.py -q
```

在隔离目录运行；生产不需要此so，不能复制Windows dll到Ubuntu。Numba基准使用正常模块导入，避免动态模块名污染缓存；源码改动后的首次编译正常，随后复用。

## 上线前和后续

上面的三个core文件已经人工确认；实际更新仍按现有维护流程，在获得对应运行操作授权后停止本安装调度并等待worker结束，整体更新。不要在运行中的初始化中途覆盖代码；本轮未执行这些动作。不需要因本次资源/实现优化改S3日期或主动清空snapshot。

需测完整框架的读取、时序因子、其他截面、选币、聚合、模拟及MODEL阶段。当前全量PKL仍一次加载，单片因子仍汇总后写出；本轮不声称已经实现Arrow IPC流式全链。如果这些阶段仍超过预算，再推进按币种分批落盘/按需读列，保持行序、NaN与传统策略输出；不先大改缓存协议。确认整轮预算后比较1/2个worker，而非仅因4核就开4进程。

服务器原先3个孤立交易子进程约5.8GiB swap仍属于独立运维事项，本轮未结束它们。旧swap占用不能直接算作本轮常驻RAM，也不能以S3单组件3.2GiB保证与其他实例同时运行时不会OOM。
