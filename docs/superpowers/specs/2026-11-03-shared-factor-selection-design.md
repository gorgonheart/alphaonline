# 因子、截面与选币共享计算设计

状态：设计已获用户确认，代码已按计划实施并完成本地重复离线验收；新入口默认关闭、未部署。本文第3节保留设计编写时的事实，最新实现及证据以共享计算复核报告为准。
日期：2026-11-03。
设计审阅：独立builder-check已完成，结论为“nothing important left”；仅表示没有阻碍制定实施计划的重大信息缺口，不代表代码或性能验收通过。

## 1. 目标与范围

用户明确要求：优先优化因子（包含截面）与选币；及时释放旧块，减少重复转换；允许修改不合理的 core 流程；优化必须覆盖初始化、续算、修订回放和正式交易，并保留框架特殊行为。允许因子阶段合理使用更多 CPU/内存，选币阶段优先降低工作集，以完整耗时而非单算子时间判断收益。

沿用上一轮推荐的渐进统一路线：通用计算落在 core，策略数学留在 factors/sections/positions，账户策略参数留在 accounts，tools 保留资源、初始化、恢复和离线测试编排。不是再建立一套 MODEL 专用因子引擎。

本轮不变更账户策略、S3 起始日期、模型方法、下单公式、自动补 BNB、上游 alpha/alpha2 发布协议；不实施 tail-only，不整体重写 MODEL/模拟数值内核，不增加数据库或新的哈希校验体系。不把重构当作改变数值容差、修正历史策略语义的机会。

## 2. 方案选择

| 方案 | 判断 |
| --- | --- |
| 只继续优化 tools 初始化 | 改动小，但4050及交易仍是另一条数据路径，不满足最新范围 |
| 统一 core 计算、保留适配、局部优化热点 | 推荐；共享因子和选币实现，逐步降低搬运和工作集，能够逐阶段对拍 |
| 一次重写全部数组引擎及 MODEL | 需要同时重做排名、状态、聚合和恢复语义，本轮验证范围过大 |

“统一”是统一计算契约与实现，不是强制每种策略使用相同任务大小、输入长度、进程数或单一 DataFrame 类型。

## 3. 当前代码与测量事实

- `core/backtest.py:run_backtest_multi` 是正常子策略入口，仍经 load_realtime_data → 因子 → 截面 → 选币 → 聚合 → 模拟。
- `tools/initialization_pipeline.py:run` 是候选初始化编排，默认开关关闭；已直接使用完整 Arrow 和统一 IPC，正常4050未接入。
- `tools/streaming_factors.py:factor_blocks` 每批收齐 worker 的完整表后由父进程写块，存在结果回传和批次等待。
- `tools/initialization_data.py:iter_blocks` yield 时持有原块；选币调用方又生成排序块，不能靠调用方 del/GC 消除生成器引用。
- `core/select_coin.py:calc_cross_sections` 因一个截面缺少 Polars 接口而让全部截面走 pandas；需要保留依赖顺序后改为按能力分派。
- S3 已有分块状态推进，但外围仍会物化全历史依赖表；TopK 有跨时间累计/shift，不能独立计算各时间块。
- `tools/robust40/handoff.py` 管理修订检测、共同恢复及目录事务；MODEL 数学与恢复在 `positions/ModelRobust40Strategy.py`，历史拆分的 live.py/runtime.py 不是当前入口。
- `tools/robust40/cli/server_robust40.py:_trade` 在账户主流程前检测修订并恢复；`server.finish_live` 在目标一致性通过后、目标仓位和实际下单前标记计算完成。

此前三组全初始化中位772.8→622.5秒，但新路径选币 private 采样最高7.72GiB。时间阶段中位：时序188.9、截面72.6、选币97.4、聚合模拟143.8、MODEL104.4秒。Windows private/提交内存不能代替 Linux cgroup 内存与swap。该基准早于17因子的新批量接口，必须重新计时，不能叠加收益。

证据：`research/initialization_refactor_20261103/performance.md`、`docs/2026-11-03-initialization-data-refactor-review.md`、`docs/2026-11-03-factor-multi-params-review.md`。

## 4. 四场景契约

正式交易是计算结果的消费场景，不另建第四套因子算法。

| 场景 | 起始状态与输入 | 共享计算要求 | 保存及执行边界 |
| --- | --- | --- | --- |
| 初始化 | 空私有状态；同轮完整140xx历史；初始化功能配置 | 全历史时序→截面→选币；初始预热、S3 origin与首个有效时刻规则不变 | 原最终 snapshot 校验/安装；初始化计算本身不下历史订单；后续交易继续原调度 |
| 正常续算/补缺口 | 有效已提交状态；4050运行窗口及原依赖准入 | 无状态短因子仍按规定窗口重算；S3、模拟、MODEL按状态续算；不能将4050误缩成新增一行 | 维持原保留区间和共同截止；中断数小时需验证缺口可补算范围 |
| 修订回放 | 当前修订输入；修订影响之前的共同恢复点 | 原状态回退后调用同一计算实现，重算受影响区间；预热输入可早于恢复点，写出区间不得混淆 | 保留子策略state0/state1、S3、MODEL共同恢复和事务；失败恢复旧状态，不能发布半成品 |
| 正式交易 | 本轮计算可来自正常续算或修订回放 | 相同因子、选币及目标结果；支持MODEL和传统仓管 | 保留当前撤单/账户检查顺序和最新目标执行；只执行本轮目标，不重放历史订单；计算已提交后的接口故障不得回滚计算 |

MODEL仍要求`incremental_lookback_hours=0`并使用共同检查点；传统策略原有`incremental_lookback_hours`行为继续保留，两者不能合并成一个隐含回退开关。

现有修订检测范围为168小时，恢复点保留25个，不扩大为全历史检测承诺。保留超出覆盖/检查点能力时转初始化的规则，不新增“微小差异忽略”阈值。

## 5. 计算边界与数据交接

### 5.1 输入、计算、状态与交易分层

1. 输入适配：沿用同轮 ready、Arrow/PKL准入、币种过滤、现货/合约映射、外部数据对齐和市场规则。上游数据只读。
2. 因子：按品种计算完整所需依赖，输出有稳定行身份的因子块；同一行情不因选币时间块重复预热计算。
3. 截面：消费完整市场截面及必要依赖列，生成与基础行对应的结果列；跨时间状态显式传递。
4. 选币：共享顺序及依赖列组，返回原选币结果语义；输出不再要求把全池全部时间块留在内存。
5. 下游：仍通过既有现货转合约、聚合、模拟、再择时、仓管与保存接口。可省重复搬运，但不借此改数学。
6. 交易执行：读取本轮目标及交易所当前资产、价格和规则；不能复用模拟用历史价格代替实时执行输入。

共同上下文需要携带：账户/offset、当前截止、输入覆盖、输出覆盖、恢复起点（可空）、只读输入位置、调用方拥有的临时目录、阶段资源预算。复用现有配置和运行上下文，不另增一套持久化运行协议。

### 5.2 行身份与布局

- 保留原始稳定行序，以及时间、symbol、is_spot；同名现货与合约必须区分。
- 原始行号用于跨列组对齐；时间排序用于截面及选币。生成行序一次、按需列取数，不以每块重置索引替代原始行身份。
- 当前品种级预处理/因子可能删行、重索引。先在原兼容边界执行并保留其输出/异常，不能假设每个函数等长、无副作用或用padding修补。
- 物理读写块、因子调度批次和计算子块是不同概念。共用时间边界及行身份，但大小由实测选择，不把所有阶段强制设成2016小时。
- 小输入优先内存交接；需要跨进程/溢出时复用统一IPC。禁止同轮同一因子集合无目的地PKL→Parquet→IPC多次转换。
- 需要报告或既有消费者的选币/权重文件继续按原配置生成；临时因子存储不能取代最终snapshot。

### 5.3 所有权与最后消费者

- 一个活跃块只由明确的任务作用域持有；生成器、闭包、Future、LazyFrame都纳入释放检查。
- 因子结果完成后交接给块存储，不让父进程同时保留完整池结果；进程任务只携带小描述，避免复制整池输入。
- 选币结束后，只保留选择结果和现货转合约必需的窄映射，不保留完整因子表。
- “释放内存”与“删除文件”分开：截面、选币、转合约映射均消费完成才删除调用方拥有的临时文件；Windows先关闭mmap持有者。
- 不改变公共目录清理责任，不引入跨账户并行；同一安装仍按现有串行交易约束运行。

## 6. 优化顺序与算法边界

### A. 因子调度与转换

先复用已完成的signal_multi_params；保持参数顺序和原signal兼容。比较两种实现：有界回传并与写入重叠、worker直接写最终分片返回小描述。以包含创建/IPC/写入的完整时序阶段决定，不能只量管道成本。

保持稳定输出顺序；过滤后实际行数才可确定全局位置，不允许并发任务争用行号。具体可采用品种顺序与品种内行号的稳定组合，或完成后一次分配偏移；实施计划须锁定一种并验证跨列组顺序，不增加逐值哈希。

4核先比较总预算内的并发，避免因子进程×Polars线程×数值库线程过量嵌套。保留spawn；允许因子工作集提高，但只为活跃计算和有界预取分配内存。

### B. 截面提速

- 按实际依赖列投影；相同依赖的参数组复用输入，组消费完释放，禁止缓存全部截面全历史。
- 逐因子选择pandas/Polars/状态接口，保留原调度顺序及必要共享字段；未知自定义截面继续原路径。
- 无跨时间状态的截面按完整市场时间块推进；不同独立因子/参数可有界并行。
- TopK按每个品种的实际有效行数维护历史（不是简单n小时），保留排名、市场规模、cum_sum/shift及缺值规则；对照完整计算。
- S3复用持仓/排名队列/首选与检查点协议。有效截面推进、缺失币、历史持仓、起始日期和排名并列行为不变。同一S3状态链顺序执行，外层分块不能让每块重新初始化。
- 不预设全面Numba/C重写；对已证实热点，可用数组/Numba替代中间表，但独立oracle必须先覆盖。

### C. 选币工作集

先解决原块/排序块共同持有，建立一次窄排序索引，按依赖相近的策略分组读取或投影。组过小导致重复IO的方案不能只因峰值低而采用。

保留现货/合约混合优先级、rank(method='min')并列、比例与固定数量、long/short数量联动、前后过滤、offset/持仓期及原物理结果顺序。标准选币使用共享块；custom、entry_exit及日频通过明确适配保留原行为，不静默当成无状态standard。

先降工作集，再比较2/3/4任务并发；不以平均CPU1.7核推导必然线性加速。第一轮保留2016小时物理块作为对照，计算子块大小可试验。

### D. 条件推进项

小选币文件可比较每策略多batch IPC file与现有分块文件；stream并非唯一方案。聚合v2另行对拍，其最终1e-9归零和累加顺序不能默认为等价。二者不阻塞A/B/C，不把MODEL重写绑入本轮。

## 7. 回放正确性专项

回放不是重新从修订时间截断行情。需区分：原始修订时间、最早受影响输出时间、共同恢复点、因子预热起点和本轮截止。

既有next_close/shift、映射和自定义钩子可能使受影响输出早于修订输入。实施前用针对性oracle验证边界；如果现有恢复点选择不足，作为正确性修复独立列明人工复核，不用更宽容差或忽略旧行掩盖。

对每个旧因子/截面明确依赖是否有限；不能证明有限的自定义函数继续全必要历史适配。回放所需历史超出可读4050及已保存状态的覆盖时，沿用明确重建路径；不能悄悄裁切后继续交易。完整初始化也必须验证完整Arrow和外部依赖覆盖，不把140xx视为任意起始日期均足够。

验收采用两种对照：同一起点/同一修订输入的新旧流程比较；构造有充分完整历史的独立全量重算作为状态恢复oracle。若旧路径自身存在差异，单独报告，不能让“与旧路径一致”掩盖回放错误。真实样本对拍须披露上游历史已被清理、外部数据或长因子预计算口径等限制。

计算提交和交易结果分离：回放计算失败恢复原snapshot；finish_live提交后交易接口失败保留已提交状态。不新增订单去重协议，不承诺当前框架未提供的exactly-once交易；仅禁止重构新增历史订单或重复执行副作用。

## 10. 性能评估与资源原则

- 因子允许合理提高活跃工作集，选币必须先降低峰值；本轮不自动提高现有Linux MemoryHigh4.5GiB/Max5GiB/SwapMax12GiB。
- 阶段结束是否退出进程由端到端测试决定，保留低成本阶段隔离；不恢复已被用户否定的逐策略/逐块进程回收。
- 从启动前计到计算保存、校验、进程退出及临时数据释放；分别标出准备/读写/转换/计算/释放。正式交易报告计算与接口等待两类耗时。
- 新基线包含17因子接口迁移；固定同轮输入、4核、依赖与缓存条件。候选先小样筛选，再至少3组成对完整测试；冷编译和暖编译分别报告，不以3样本宣称P95。
- 初始化、正常4050、可覆盖缺口、一次有效修订回放分别计时；正式交易用离线mock排除网络抖动，并保留原目标/订单参数核对。
- Windows记录进程树private/提交峰值，Linux记录cgroup anon/file/swap、pressure及完整时间，不能互换口径。Linux实际测试和部署按单独明确授权执行。
- 硬性验收：结果/状态/副作用契约通过、无OOM、四场景功能完整。性能采用成对报告，若目标阶段或整轮代价超过样本波动，保留旧路径并说明取舍；没有固定承诺节省秒数或选币1–2GiB。
- 不因降低内存而接受明显更慢的实现。先处理副本/生命周期，再调分片与并发；只有收益明确才启用候选。

## 11. 分阶段路线与人工审核

这是设计路线，不替代批准后逐任务TDD实施计划。

1. 建立四场景离线契约和最新基线，补恢复影响起点的oracle；产物是可复现基准和风险清单。
2. 统一数据所有权与块接口，解决未排序块持有；先不改变排名和因子数学。
3. 共享因子调度，比较回传重叠与直接写分片，接通初始化/续算/回放使用者。
4. 截面依赖复用、逐因子适配，再逐个实现有状态分块；每个截面独立RED/GREEN对拍。
5. 选币列组/排序/工作集优化，测2/3/4并发，保留特殊策略适配。
6. 四场景贯通和失败恢复、正式交易mock验证；独立core变更清单人工复核后决定启用与Linux验证。
7. 小文件合并/聚合v2仅在前面测量证明值得时另批推进。

每批交付必须说明修改文件、保留功能、是否取消旧分支、测试证据、完整耗时/内存取舍和回退方法。回退以已核验代码和原snapshot协议为基础，不清生产数据、不靠重新训练掩盖回归。

审核重点：四场景覆盖；共同恢复与执行副作用边界；共享core特殊策略适配；资源上限保持不变；同源输入/完整性能口径。设计批准后使用writing-plans编写准确函数接口、文件级任务、失败测试与验证命令，再进入实施。
