# 修订超出恢复范围：即时转后台重建设计

状态：用户已批准，2026-11-05本地实现并通过相关离线回归；未部署、未修改生产数据或服务。承接当前next-runtime-efficiency分支，保留该分支已有优化。实际范围与限制见 ../../2026-11-05-rebuild-handoff-implementation.md。

## 目标与已确认决定

用户确认：发现必须完整重建时立即启动/登记后台初始化，初始化成功后仍在下一合法offset交易；不增加立即追赶下单，不补历史订单。普通续算、恢复点内回放、S3/子策略/MODEL共同状态及传统账户行为保持。

“立即”指不再把可预期的重建需求抛到startup系统异常/10秒重试循环，不再等下一个账户offset才开始安排重建。具备完整同轮行情时立即计算；缺完整行情时立即申请、等待数据，不能凭4050/5000短发布造完整模型。上游若只在下一合法offset发布全量，则数据等待仍可能持续到该时刻；本设计不新增同stamp覆盖发布、盘中补算API或上游重启。

## 根因与当前行为

本地源码链路：replay.before/common_before找不到修订之前的共同恢复点→ValueError→handoff清理失败回放工作区→CLI _trade捕获后begin写complete=False再raise→worker退出1→startup subprocess.run(check=True)抛CalledProcessError→外层报警、睡眠、重新进入5分钟调度。标记和清理已有，缺的是有类型的重建结果及本轮交接。

当前恢复检查在执行任何账户交易前，适合作为自动重建边界。交易计算已提交后的订单/接口异常不属于此边界，不能触发状态回滚或自动重建。

用户提供的15m范围说明表明该轮无可用旧恢复点；最新粘贴的35m只有外层尾部，不能据此认定其内层错误和15m完全相同。本设计处理同类“明确不可回放”的状态，不以截断日志字符串决定动作。

## 方案取舍

1. **采用：明确重建结果→现有Coordinator接管后台初始化。** 保留账户隔离、资源监督和下单调度；需要startup窄接线。
2. 不采用交易worker直接同步初始化：当前worker已加载续算profile、持有snapshot锁，直接重载/递归既易锁冲突，也会阻塞其他账户。
3. 不采用任何非零退出都删数据重建：磁盘满、权限、代码异常、网络/交易错误不能靠重复训练解决，可能形成循环并抹掉诊断数据。

## 控制流程

1. 在共同恢复点选择失败处抛有类型的重建异常，仍可继承ValueError保留离线调用契约，携带修订时间与原因。不要用字符串匹配现有ValueError。
2. _trade仅将明确不可续算/不可回放的状态转为rebuild_required；先完成事务恢复/临时目录回收，持原账户锁写complete=False，再释放锁并返回专用进程结果码。日志记录这是恢复交接，未提交、未下单，不冒充普通成功。
3. startup只对MODEL专用结果码调用Coordinator的重建接管入口，然后继续其他账户；不运行该失败轮的统计。普通成功照旧统计，其他非零码仍走原异常处理。不能仅凭complete=False就把任何错误吞掉；不能让传统core/account_exec的同数值退出码触发MODEL重建。
4. Coordinator立即登记本账户全量Arrow需求，复用已有后台任务跟踪；不重复发起同账户重建。已有状态检查发现configuration/gap/incomplete时也复用该入口，避免形成两套初始化生命周期。
5. 当前同offset四ready、两份full_history Arrow和必要列齐全时，采用最新完整同offset发布的stamp，进入原冻结→完整计算→共同校验→原子安装流程。
6. 数据不足时保留轻量等待任务。只检查该offset就绪标记及变化后的Arrow头部，不读整段行情、不创建冻结数据/完整snapshot副本、不占全局计算槽。建议2秒检查一次，状态变化时才输出日志；达到既有240秒等待窗口仅记一次等待原因，不当作计算超时或反复重启。上游联动未启用则明确提示需上游全量发布，仍可等待人工重建完成。
7. 排到计算槽后再次检查publication：上游仅保留最新轮，排队期间可能换轮。重新选择同offset最新完整发布，工作区和冻结输入统一实际stamp；已打开日志保留排队stamp并记录publication_stamp；冻结稳定性失败仅等待新发布，不混用旧ready与新行情。
8. 已被其他有效任务完成重建时，在持锁检查后取消重复任务。初始化成功后释放全量需求、清理自有工作区并结束；本设计不在后台执行订单。正常交易仍由下一合法offset进入。

等待控制器的实现归工具层，可复用既有监督进程。必须满足：同账户最多一名持锁负责人；等待不占global_initialization_slot；取槽后重查数据；计算仍在现有资源限额内；不得重复获取同一非重入初始化锁；startup退出/恢复不造成多个账户任务反复堆积。具体函数拆分由实施者决定，优先共享轻量等待控制器/线程，不为每个待数据账户常驻一个加载完整MODEL依赖的重进程；不能为此引入新常驻服务或全盘扫描。

## 异常分级与防循环

| 情况 | 处理 |
|---|---|
| 无共同恢复点早于修订，或明确历史状态不足 | 标记需重建，立即交接 |
| inspect已判定配置变化、状态缺失/损坏、缺口超续算容量 | 使用同一重建接管入口 |
| 当前同轮行情未就绪/只有短Arrow/发布切换中 | 等待数据；不先毁掉正式snapshot |
| 参数所需历史超过现有上游历史、S3日期本身无效 | blocked/configuration，保留诊断，不能在同配置同数据上无限重算 |
| ENOSPC、权限、导入/程序异常、非预期格式错误 | 保留真实错误；不把它们自动解释成缺恢复点 |
| 状态已提交后交易所/订单错误 | 保持已提交状态，沿原交易错误处理，绝不重建后重下同一历史轮 |

同一配置与同一publication的确定性初始化失败只执行一次，沿用attempts去重；新配置/新发布可以再评估。等待就绪不算计算失败，不每2秒创建新任务/日志文件。进程重启后的恢复仍靠现有元数据、OS锁和工作区生命周期，不增加第二套状态台账。

## 清理边界与空间

立即清理的是该账户已退出的失败回放stage、旧初始化scratch；清理前遵守现有锁/活跃进程判断。数据目录整体、其他offset、账户交易记录和上游行情不得删除。

正式旧snapshot写complete=False后保留到新包验证并安装成功；原安装协议只保留一份.previous。新包不复用失效计算状态，因此无需先删旧包来“强制重算”。这会保留重建期间旧包+新工作包的既有峰值，不能声称零空间成本；空间不足保留错误，不能自动扩大删除范围。

若失败回放已清理，不再次复制/清理它。优先复用原cleanup计时。提前发现无恢复点可避免无用copy，但不能为此增加每轮索引写盘或重复读取完整MODEL大包；这项只在改动分支内能复用已有读取时实施，否则单独评估，不阻塞控制流修复。

## TDD与验收

- 无共同恢复点：重建结果明确，complete=False，未调用账户交易入口，startup不抛通用重启异常，同轮接管一次。
- 足够恢复点：既有回放结果和持久化逐值一致，仍只执行当前一轮交易。
- 当前完整Arrow就绪：立即使用相同offset一致stamp，S3/子策略/MODEL结果对照原显式初始化相同输入。
- 短Arrow/缺ready：先注册全量；就绪自动开始；等待阶段无大数据读写、不占计算槽，其他已就绪offset不受阻。
- 排队换轮、重复交接、startup重启、初始化进程中断：最新完整发布一致、同账户单实例、锁释放、工作区有界。
- 磁盘满/权限/配置错误/订单错误不被误归类；初始化确定性失败不无限循环。
- 传统45m账户路由、正常MODEL成功轮统计、dry_run/none原调用顺序保持；所有验证拦截网络交易。
- 正常轮新增成本应仅为子进程结果分支，无额外读行情/状态；记录异常轮的交接、等待、资源排队、冻结、初始化及清理耗时，不能只报内核时间。用户提供0.16/0.17秒仅是历史清理耗时，不推为本功能恢复总时间。
