## 方案比较

1. 整文件替换：会恢复上游动态杠杆实现、丢失干跑门、统计接口、余额请求 recvWindow=30000 和本地负余额处理，不采用。
2. 三方增量合入、每轮计划金额限制：用户已选择限额语义；推荐采用此方案，局部补配置校验与名单失败边界。钱包补丁单独证明，不扩展数据计算主链。
3. 严格小时累计额度：需要定义账户身份、时区、预占、部分成交、未知回执、重启和并发协调；用户未选择，本轮不实现。

这是涉及真实订单与资产输入的中等范围升级，不能以“只改两个文件”估计风险；但无需重写因子或重跑全市场历史研究。

## 限额语义和边界

- 配置保持 `max_symbol_order_amount`，默认 `{}`；显式币种优先于 `'*'`，都没有则不限。示例 `{'*': 300, 'ABCUSDT': 200}`。
- 在 `calc_order_amount` 中，聚合目标与实际持仓差额、取得参考价之后，拆单之前，对 `(symbol, symbol_type)` 行裁剪。现货与合约分别获得完整额度，不是两市场合计额度；账户之间不合并。
- 仅调整本轮实际数量与计划金额，不改目标仓位、选币、模拟净值、MODEL/S3 状态。下一轮根据**最新目标及最新实际持仓**重算差额，不保存“必须补发的旧订单队列”。目标变化会改变余量。
- 建仓、加仓、减仓、清仓、调仓都受限，保留上游交易模式与 IOC/GTC 路由。清仓 1000U、限额 200U 时本轮只计划退出 200U。调仓被裁剪成仅减仓后仍保留调仓标签，是上游兼容行为，测试必须覆盖其 reduceOnly/GTC 路由。
- 按每轮调用裁剪，不计同小时累计；同小时重新计算仍可获得新额度。正常每账户每小时一轮时才近似公告中的“每小时”。现有恢复逻辑保持，不能称新增了幂等保护。
- **限制的是参考价格下的计划名义金额，不是最终成交或限价委托的绝对上限。** 原数量精度、拆单及 IOC 滑点逻辑保留。离线例：296U、价格100、数量2.96，在合约0.1数量精度下提交3，参考金额300U；1.5%买入限价对应304.5U。严格提交金额上限是另一项交易规则改造，本轮不顺带实施。
- 原缺报价填1的容错不能证明限额有效；新字段启用时，对受限行缺失、零、负或非有限参考价，应在订单计算阶段明确失败并阻止该账户本轮发送，而非以1继续。关闭限额的路径保持原行为。
- BNB补币、保证金调整、独立下架清仓工具等绕开 `calc_order_amount` 的操作不在该限额内，不宣称限制账户所有交易。

### 配置校验建议

上游将低于 `max(现货最低金额, 合约最低金额)` 的配置删除，会使该币变成通配限额或无限额；例如仅合约的7U限额被现货10U门槛删除。不能把这种失效叫作正常风控。

建议在账户构造时要求字典、非空字符串键、有限正数值（拒绝 bool、NaN、Inf、字符串、0、负数），非法配置明确报错，不静默删条目。允许低于交易门槛的正数限额；执行时保留现有市场最小金额过滤并给出说明，不能为了凑最小订单而放大该计划额度。市场实际 min_notional/数量精度仍由原执行器校验，不改全局门槛。

## bStocks 兼容与性能

上游把两个接口结果合并，并非仅主接口失败才请求第二接口。必须保留两来源合并，否则主来源成功但缺股票币时兜底无效。全半角归一化只用于名称括号，不改资产代码/交易对映射。

继续沿用无API不请求、filter_bstocks=False不请求、有效12小时缓存不请求的路径。两次调用只在需刷新时发生，但类缓存属于进程内；新子进程、冷启动及网络重试会有成本，不能声称整个升级零耗时。

原版存在：钱包接口成功返回空名单、第二接口失败时，旧名单被清空并刷新时间戳。建议局部修正为：

1. 两来源都成功：用本次并集合替换，允许确认后的空集合。
2. 部分成功：保留旧名单并合并本次成功结果；有可信非空结果时可更新时间戳，仍记录失败来源。后续完整成功刷新才移除旧成员。部分成功可能暂缓移除旧成员至缓存过期，这是保守取舍。
3. 冷启动且部分成功结果为空：不写成功时间戳，保持本地 MODEL 初始化拒绝未知名单的保护。
4. 都失败：保留旧名单及旧时间戳。

响应需按预期列表/字段校验，异常响应不能当有效空集合。不引入磁盘名单缓存。保留 `apply_bstocks_black_list`、共享因子 worker 参数及 MODEL 初始化传递链；名单变化会有意改变选币池，不能把这种变化误报成 Polars/C 因子数学回归。已有 MODEL 历史是否需重建必须单独对照实际名单变化，不自动删除状态。

## 统一账户钱包补丁：必须分开验收

当前 `get_swap_usdt_balance` 注释写“直接返回0”，**实现却读取 UM crossWalletBalance**；`get_account_overview` 把它放入 swap equity。`AccountConfig.update_account_info` 取得 spot/swap equity，`core/position.py` 将两者相加计算目标仓位。

离线调用当前和上游实际 `get_account_overview`，用一致的合成余额：杠杆可用100、UM钱包20、UM crossWalletBalance20、无持仓浮盈。

| 路径 | spot equity | swap equity | 目标仓位资金合计 | account_equity |
|---|---:|---:|---:|---:|
| 当前本地 | 100 | 20 | 120 | 100 |
| 直接上游2.3.3 | 120 | 20 | 140 | 120 |

因此上游修复某个概览字段的同时，可能让本地实际目标资金重复增加。此例证明条件性冲突，不代表真实线上响应已被验证。不能把 UM wallet 与 crossWalletBalance 在任何账户状态都假定相等。

**建议首批保留当前交易资金分解，暂不机械合入此两行。** 将钱包项作为同一升级分支内的独立核算任务：先明确各响应字段、正负余额、锁仓、USDT/USDC、UM/CM及浮盈的唯一归属，独立 oracle 验证每项只计一次，且统计专用 actualEquity 视图保持。没有这一证据时，不能以改 spot、置 swap=0 或简单相减作为修复，也不能宣称完整2.3.3已完成。是否最终调整交易资金分解需展示具体补丁及前后数值再确认；其他明确增量可先实现和验证。

保留本地负余额不钳0、30秒只读余额recvWindow、统计接口及原持仓过滤。不得扩大到收益/成本统计重构。

## 依赖与加速链路

本机只读查得：xbx-py11=0.1.23、ccxt=4.5.53、NumPy=2.0.2、pandas=2.2.3、Polars=1.36.1、PyArrow=17.0.0、Numba=0.60.0；现有ccxt实例没有 `sapi_get_equity_market_tokenized_assets`。

核对 [PyPI 0.1.24 元数据](https://pypi.org/pypi/xbx-py11/0.1.24/json)，其声明固定 ccxt=4.5.88，上述数值计算依赖版本未变。因此建议固定 xbx-py11=0.1.24、ccxt=4.5.88，两个 requirements 同步；不执行不受控的 `pip install -U`，不直接改共享alpha311。

实施时先在隔离依赖位置解析/验证安装结果，确认新接口、Binance/OKX原接口、依赖一致性。xbx发布包还可能携带代码，依赖声明不变不等于整个包无行为变化。固定已验证结果，不升级NumPy/Numba/Arrow/Polars，不需要因本次功能重编译C；若实际解析结果改变这些库，则重新评估ABI和跨项目验证，不能强行忽略依赖。

订单限额位于因子/模拟之后；没有直接修改数据格式、预计算列、完整历史长度、C公式、Arrow回退和MODEL状态协议。未发现源码层面的性能优化覆盖冲突，但增加名单请求、名单变化和依赖升级均需专项验证；本轮没有整轮性能实测，不能承诺无性能回归。
