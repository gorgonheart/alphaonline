## 推进顺序与依赖

1. D2规范贯穿每项开发；D1与P1是独立事项。Arrow协议设计未定不应阻塞P1自身的设计和离线验证。
2. 性能改造保留原先顺序：**P1重复编译 → P2模拟行情复用 → P3资金曲线/再择时交接**，逐项做独立oracle/TDD及端到端成本对照。
3. P4真实执行观测单列，不等待P2/P3结束；只能在已获授权的真实运行中观察或增加必要统计，不能为了采样自行启用none/发单。先解决P1，再评估相邻ticker是否可用同一执行快照，避免改变报价新鲜度和拆单金额。
4. D1上线验证后重测P5，避免将“发布变短”和“读取器优化”收益重复相加。P6、O1/O2/O3保留在清单，按新增证据决定实施，不自动扩大重构。
5. 上线前统一执行D2专项：所有新落盘点、故障残留、硬链接持有、缓存失效、测试目录可删除性与资源峰值。

## 计算与交易边界

- P1保留死区、执行上限、手数截断、纯多预算、开仓/清仓/翻仓、无效活跃价格处理。新进程冷启动与跨进程缓存命中分别测，不能只测同进程热调用。参数显式传入，覆盖参数变更和缓存失效。
- P2保持上期价格、未平历史币种、退市列、资金费率与手续费；worker内共享只读行情，独立对齐结果，避免跨账户/轮次可变缓存。
- P3保留不同hold_period、分钟偏移、首尾不完整周期裁剪、ffill/dropna及共同起点；不能因只轮动部分子策略就删其他子策略Bias。初始化已具备的共享输入不倒退。
- P4保留临近下单账户刷新、自动补BNB、现货卖→合约→现货买、TWAP/GTC/IOC和重试语义；分别记录计算提交、订单请求成功、最终失败、成交状态，不能将回执等同全部成交。
- core允许在必要的数据交接边界最小改动，但不整体替换。每批列出实际core/startup修改和传统策略影响，新增统计不引入验证门禁。
- 新测试/对拍/采样文件全部位于生产test；不新增全量行情或snapshot长期采集，不改有效状态格式来迁就测试。

## 验收矩阵与成本口径

| 场景 | 必须关注 |
|---|---|
| 完整初始化 | 完整因子、S3、子策略、MODEL同截止；全量请求与成功安装；进程创建/IPC/释放成本 |
| 普通4050续算 | 权重与目标手数严格一致；新worker缓存实际命中；工作集和中间文件有界 |
| 缺口、跨日、新季度 | 数据需求、日级特征、季度训练/复用与旧版一致，不用普通小时耗时外推 |
| 修订回放 | S3/子策略/MODEL共同恢复；回放输出、持久化和清理一致，状态提交后订单错误不回退 |
| 真实交易 | 固定执行输入离线对拍；真实运行分段观测不改变路由/资金等待，调用与成交结果分开 |
| 传统策略 | 用指定45m传统配置验证共享core变化，覆盖代表性offset和hold_period；不把单一45m通过宣称全部策略已验证 |

复用现有冻结证据；每次只测受影响路径，只有改到共享流程才扩大相应回归。性能比较包含导入、创建、编译、读写、序列化、计算和释放；记录冷/热缓存、并发、内存、swap、磁盘峰值及清理耗时。嵌套阶段不相加，小样本不报P95，阶段耗时不等于可节省量。

## 联动现状与必须保留的语义

- alpha/config.py的publish_kline_num当前全局0；0=全量，正数只在最终Arrow发布时裁剪。原始PKL、长因子计算、Pivot完整历史应保持，不随发布4050而缩短。
- alpha/core/preprocess.py在每个市场发布函数中直接取全局配置；目前无跨消费者通知协议。
- alphaonline初始化freeze_inputs(full_arrow=True)检查full_history元数据，缺全量即失败。普通MODEL原始特征已显式tail=4050。
- 初始化完成定义应是S3/子策略/MODEL同截止校验、complete和install完成；不能仅以子进程exit=0判断，prepare可能因为状态更新而正常取消。
- 切换影响下一轮新发布，不能覆盖已发布同stamp的文件；保留单轮Arrow原子发布及冻结硬链接语义。成功安装与清理失败需分别记录，不能清理错误使有效状态回滚。
- spot/swap必须共用在本轮开始确定的发布深度，不能各自读取瞬时请求导致一边全量、一边4050。
- 同offset多个账户或两个alphatrade安装必须合并需求；只释放自己的请求。初始化失败保留需要全量的意图，不能无限追加请求文件。
- 4050回放不能覆盖的历史继续走已有重新初始化规则，并重新请求全量，不静默使用截断行情。
- 当前已发布4050时收到全量请求，不能重试旧stamp期待其变长；等待下一合法完整发布。启动越接近offset，越需明确该边界。

## 待确认方案

推荐同机共享数据目录中的按消费者/offset需求文件：alphaonline请求完整历史，alpha在轮次开始统一解析；全部相关消费者成功释放后，后续轮次发布4050。文件是业务控制状态，不在test，无HTTP服务、无周期性重启或改写机器config.json。

备选为HTTP控制接口：适合真正跨主机的消费者，但增加服务、权限、重试和部署维护。目前上下游通过本地路径共享行情，没有必要先引入。

不推荐直接由单账户改全局publish_kline_num/config.json：覆盖其他offset/消费者需求，且现有进程未必重新读取该配置。

尚需在确认推荐方向后明确：启用联动时未注册传统消费者的基准深度、消费者身份来源、失败/停用请求如何显式撤销、通知写失败如何在下次启动补发、同轮深度向两个市场任务传递的位置。不得用超时自动判定初始化成功，也不必增加完整状态台账或全盘扫描。

验收应覆盖全量→初始化安装→4050、失败重试、进程中断、同offset多消费者、不同offset隔离、spot/swap同深度、迟到请求、重新初始化、全量末4050与直接4050逐值相同、跨日MODEL与修订回放；测试只在本地或服务器test，保留现有协议检查，不启动实盘。
